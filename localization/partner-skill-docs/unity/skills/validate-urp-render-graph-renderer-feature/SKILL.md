# 技能：验证 Unity URP Render Graph 渲染器特性

## 目的
审查 Unity 6+ URP Render Graph `ScriptableRendererFeature` 及其关联的 pass 实现中与材质绑定、资源接线、渲染图纹理创建、静态渲染函数结构、全局资源暴露以及 API/版本使用相关的正确性问题。

## 何时使用
在以下情况下使用本技能：
- 审查 AI 生成的 Unity URP Render Graph 渲染器特性代码
- 在集成自定义 `ScriptableRendererFeature` 之前验证它
- 检查常见的 Render Graph 资源接线和 pass 设置错误
- 诊断可疑但看似合理的 Render Graph pass 实现
- 审查自定义 raster/blit/copy pass 是否使用了最合适的 Render Graph 辅助 API

## 输入
本技能应期望：
- **Unity 版本**
- **URP 版本**
- **要审查的 Render Graph 渲染器特性代码**
  - `ScriptableRendererFeature`
  - 关联的 pass 代码
  - 或两者
- **预期行为**
- **预期输入/输出**（如已知）
- **可选约束**
  - 项目约定
  - 所需的 pass 类型
  - 已知资源
  - 所需的材质/着色器属性

## 输出格式
本技能必须按以下结构返回结果：

### 1. 验证摘要
对实现的简短总体评估。

### 2. 已确认的问题
由所提供代码直接支持的具体问题。

### 3. 可能的问题 / 有风险的假设
取决于缺失上下文或不完整信息的潜在问题。

### 4. 建议的修复
针对每个问题的最小针对性修复。

### 5. 修正后的代码段
在有帮助处提供小型修正代码段。

### 6. 缺失的信息
以更高信心验证代码所需的任何信息。

## 验证清单

### 1. 材质绑定
检查：
- 材质是否被清晰声明
- 序列化材质在需要时是否正确暴露
- 材质是否正确传入 pass
- 在需要处是否存在 null 处理
- 声明的材质是否实际被使用
- **所有必需的材质输入是否在执行前绑定**
- **当着色器期望主输入纹理时，主输入纹理是否被显式绑定**
- 辅助纹理和参数纹理是否也被显式绑定
- 纹理/属性绑定是否匹配着色器期望的属性名称

在以下情况标记为问题：
- 声明或传入了材质但实际未使用
- 只绑定了辅助纹理或参数，而省略了主输入纹理
- pass 绑定了遮罩/噪声/辅助纹理但未能绑定主颜色/输入纹理
- 假设必需的着色器属性存在而未经设置
- 属性名称不一致或有歧义
- 当 pass 模式要求显式绑定时，代码依赖隐式主纹理绑定

优先采用以下模式：
1. 材质被清晰创建或分配
2. 主源纹理被显式绑定
3. 所有辅助纹理被显式绑定
4. 属性名称一致且有意图
5. null 或缺失资源的情况被处理或报告

### 2. 纹理资源接线
检查：
- 采样/读取纹理、写入目标和辅助纹理是否被清晰区分
- 与 `UseTexture(...)` 一起使用的纹理是否适合读访问
- 与 `SetRenderAttachment(...)` 一起使用的纹理是否适合作为写入目标
- 源、目标和辅助资源是否未被混淆
- 所有预期的纹理是否被显式接线
- 涉及材质时，纹理属性名称是否显式且一致
- 实现是否未凭空捏造纹理可用性
- 多纹理资源的使用是否被显式而非隐式处理

在以下情况标记为问题：
- 意图作为输入/读取资源的纹理被用作写入目标而无正当理由
- 目标/写入目标与采样输入混淆
- 辅助纹理在未被清晰来源或接线的情况下使用
- pass 设置中缺少必需的纹理资源
- 读/写资源角色有歧义或不一致

### 3. 执行结构 / 静态渲染函数
检查：
- 渲染函数是否声明为 `static`
- 执行结构是否匹配目标 pass 类型和 API 风格
- pass 数据是否正确接入执行
- 资源是否在正确的阶段被访问
- 执行逻辑是否与预期的渲染 pass 行为一致
- 渲染函数使用的每个 `PassData` 字段是否在针对当前录制的 pass 设置期间被显式赋值
- 实现是否不依赖默认值或先前赋值的 `PassData` 状态
- 存储在 `PassData` 中的资源句柄是否针对当前帧/pass 录制重新赋值，且未从先前使用中留下悬空

在以下情况标记为问题：
- 渲染函数不是 `static`
- 实现使用实例方法而 API 模式期望静态渲染函数
- pass 数据或必需资源通过实例状态而非提供给静态函数的 pass 数据/上下文访问
- 执行流不匹配预期的渲染图或 pass 执行模式
- `PassData` 字段在渲染函数中被读取但在 pass 设置期间未被清晰赋值
- 只有部分 `PassData` 字段被重新赋值，而其他字段可能保留来自先前池化使用的陈旧值
- 存储在 `PassData` 中的资源句柄可能由于不完整重新赋值而从前一帧或 pass 残留
- 由于 pass 数据在每次录制时未完全初始化，实现有使用悬空或陈旧句柄的风险

优先：
- 在每次 `RecordRenderGraph(...)` 调用期间显式为 pass 使用的每个 `PassData` 字段赋值
- 将 `PassData` 视为按录制瞬态的数据，而非持久状态
- 避免对池化 pass 数据对象进行部分初始化

### 4. Render Graph 描述符验证
检查：
- 当可以直接使用适当的图派生描述符时，实现**不**默认创建新的 `TextureDesc`
- 当纹理应匹配活动渲染目标时，描述符首先从相关的渲染图资源获取，例如：
  - `resourceData.activeColorTexture.GetDescriptor(renderGraph)`
  - 或其他适当的现有图支撑资源
- 获取描述符后，只修改实际需要不同的字段
- name、depth bits、format 和 MSAA 等描述符字段被有意保留或有意覆盖
- 对描述符数据的任何手动重建都有特定需求作为正当理由

在以下情况标记为问题：
- 代码创建全新的 `TextureDesc` 而未先尝试复用图派生的描述符
- 默认将宽度和高度手动复制到新描述符结构中
- 当有更准确的渲染图派生描述符可用时，将 `cameraTargetDescriptor` 用作主要来源
- MSAA、图形格式或与活动渲染目标的兼容性等重要属性被意外丢弃
- 描述符重建被用作便利捷径，而非与源资源的必要偏离

首选的规则：
- **除非无法直接使用图派生的描述符，或纹理必须有意偏离源资源，否则不要创建新的 `TextureDesc`。**

首选模式：
1. 从相关的渲染图资源获取描述符
2. 只修改必须更改的字段
3. 尽可能从该派生描述符创建纹理

示例：

#### 首选
```csharp
RenderTextureDescriptor desc = resourceData.activeColorTexture.GetDescriptor(renderGraph);
desc.depthBufferBits = 0;
desc.name = "New name";
// other desired paramters
passData.targetTexture = renderGraph.CreateTexture(desc);
```

### 5. 手动复制 Pass 简化
检查：
- 当内置 Render Graph 辅助 API 足够时，简单的纹理复制操作是否未被实现为完整的自定义 raster pass
- 仅读取一个纹理并将其原样写入另一个目标的 pass 是否在适当处被简化
- 实现是否优先为目标 API/平台上下文使用最合适的内置辅助 API
- 当当前环境中应优先使用更兼容的 `AddBlitPass(...)` 重载时，是否未默认推荐 `AddCopyPass(...)`

在以下情况标记为问题：
- raster pass 仅为将一个纹理复制到另一个而存在
- pass 不使用材质也不进行自定义处理
- 渲染函数仅执行简单的 blit/复制等价操作
- 实现使用完整的自定义 raster pass，而内置 copy/blit 辅助 API 会更直接地表达相同行为

优先：
- 对于直接类似复制的操作，当这是推荐且更兼容的路径时，使用适当的 `AddBlitPass(...)` 重载
- 仅当明确适合且目标 API/平台上下文支持时使用 `AddCopyPass(...)`
- 仅当复制需要额外逻辑或非平凡行为时才使用自定义 raster pass

### 6. 手动 Blit Pass 简化
检查：
- 当 `renderGraph.AddBlitPass(...)` 会更直接地表达相同行为时，直接的全屏材质 blit 是否未被实现为自定义 raster pass
- 自定义 raster pass 是否仅在确实需要额外逻辑或非平凡行为时才用于 blit
- 简单的源到目标材质 blit 是否使用最直接的可用渲染图辅助 API

在以下情况标记为问题：
- raster pass 读取一个源纹理并写入一个目标纹理
- pass 使用材质但没有额外的自定义 pass 逻辑
- 渲染函数仅执行简单的全屏 blit
- `renderGraph.AddBlitPass(...)` 会更清晰地提供等价结果

优先：
- 对于直接的全屏材质 blit 使用 `renderGraph.AddBlitPass(...)`
- 仅当确实需要额外逻辑、多个操作、条件行为或特殊设置时才使用自定义 raster pass

### 7. 全局资源暴露
检查：
- 除非明确要求或下游消费者清晰需要，否则纹理和缓冲区不全局暴露
- 当渲染图 pass 中需要全局暴露时，实现是否使用适当的渲染图发布机制
- 是否未使用直接命令缓冲区全局状态变更作为渲染图资源发布的替代品
- 全局暴露是否未不必要地延长资源生命周期或减少混叠机会而无正当理由

在以下情况标记为问题：
- 在没有清晰消费者的情况下使用 `SetGlobalTextureAfterPass`
- 在渲染图 pass 内使用 `context.cmd.SetGlobalTexture(...)`，而渲染图资源发布才是适当的机制
- 全局暴露被用作便利捷径而非显式的 pass 到 pass 接线
- 不必要地引入隐藏耦合
- 全局暴露的纹理可能因下游 `UseGlobalTexture(...)` 或 `UseAllGlobalTextures()` 使用而被保持存活更长时间，增加内存压力或减少混叠机会

优先：
- 默认不进行全局暴露
- 尽可能显式资源接线
- 仅当渲染图中确实需要全局发布时才使用 `builder.SetGlobalTextureAfterPass(...)`
- 资源生命周期尽可能保持局部和短暂

### 8. 渲染器特性输入声明
检查：
- `ScriptableRendererFeature` 及其关联的 pass 在需要时使用 `ConfigureInput(...)` 声明所需的管线输入
- 请求的输入标志是否匹配特性的预期行为和可见资源使用
- 当目标 API 模式要求时，pass 是否未在未声明的情况下依赖管线提供的输入
- 是否未默认声明不必要的输入请求，尤其是当它们可能引入额外复制、中间资源或可避免的管线工作时

在以下情况标记为问题：
- 特性的 pass 使用或明显意图使用管线提供的输入但未用 `ConfigureInput(...)` 声明它
- `ConfigureInput(...)` 请求特性/pass 似乎不使用的输入
- 声明的输入标志不匹配预期的效果行为
- 效果描述、代码和声明的输入暗示相互冲突的需求
- 不必要的声明输入可能强制额外复制、额外 pass 工作或其他可避免的性能成本

分类指导：
- 当代码清晰显示使用了必需输入但未声明时，标记为**已确认问题**
- 当预期效果暗示必需输入但可见代码未完全证明着色器/资源使用时，标记为**可能问题**
- 当不必要的输入声明可能引入额外复制或其他可测量的运行时成本时，将其视为更高严重性

## 护栏
本技能必须：
- 避免发明不受支持的 API
- 区分**已确认**问题和**可能**问题
- 优先使用最小针对性修复而非大范围重写
- 解释每个问题为何重要
- 指出隐藏耦合和不必要的全局状态
- 说明所提供的代码何时不足以完全确定

## 非目标
- 保证运行时正确性
- 除非必要，重写整个渲染器特性
- 验证无关的玩法逻辑
- 除非与 pass 接线或绑定直接相关，验证着色器内部

## 评估标准
成功的验证应：
- 捕获真实的接线和 API 问题
- 识别可疑但看似合理的错误
- 提供可操作的修复
- 避免虚假的确定性
- 提升对生成的渲染 pass 代码的信任

## 未来扩展说明
当发现新的反复出现的问题时，用额外规则扩展此清单，例如：
- pass 排序 / 注入点验证
- 资源生命周期和清理检查
- 读/写危险检测
- 不必要的复制或分配
- 相机深度/颜色依赖验证
- 多 pass 依赖验证
- 覆盖材质正确性
- pass 配置
