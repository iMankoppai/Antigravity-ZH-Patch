# 埋点指标

为 FME 指标接入所需的 `track()` 调用，然后验证事件确实到达——不要仅凭代码更改就宣布成功。Key = 与 `getTreatment` 使用的同一 key（归因事实）；值单位必须匹配指标的 `format`（ms vs s、美元 vs 美分）——错误的单位会静默产生错误结果。相关：`/create-metric` 创建指标；`/choose-metric` 推荐使用哪些指标。

## 工具

通过 Harness MCP 服务器或 Harness CLI 工作；名称来自 [tool-map.md](../../../references/fme/tool-map.md)。

| 操作 | MCP | CLI |
|-----------|-----|-----|
| 获取指标 | `harness_get` · `fme_metric` · `params: { metric_id }` | `harness get metric <id> --json` |
| 获取事件类型 | `harness_get` · `fme_event_type` · `params: { event_type_id }` | `harness get event_type <event-name> --json` |

## 说明

### 阶段 1：确定范围

参见 [scope-establishment.md](../../../references/scope-establishment.md)。在进行任何 get 操作之前确认 Harness 组织和项目，与本地应用代码仓库和目标运行时环境分开。绝不要从代码仓库名称推导 Harness 范围。如果应用源码或运行时访问不可用，停在指导层面，并将实现/交付标记为未验证——CLI/MCP 访问并不授予应用访问权限。

### 阶段 2：检测 SDK

先搜索现有 FME `track()` 调用——它们一次性给出签名、键来源、流量类型和包装器；照着它们做。SDK 检测（搜索现有 `track()` 调用或依赖清单）以及区分它是客户端还是服务端 SDK（二者有不同 `track()` 签名）参见 [sdk-patterns.md](../../../references/fme/sdk-patterns.md)。如果此应用中还没有功能标志评估包装器，版本感知的 SDK 设置、身份、就绪和回退指导参见 [language-guidance.md](../../../references/fme/language-guidance.md)——此技能向应用现有的 SDK/包装器添加一个 `track()` 调用，不设计该包装器（那是 `/instrument-feature-flag`）。

### 阶段 3：需要时安装并初始化

从锁文件检测包管理器。**停止条件：** 如果没有 SDK，提议适合运行时的 SDK/包，并在安装或更改其版本之前获得确认。

确认环境、客户端/服务端模式，以及现有的环境变量或密钥管理器**引用**，而非其值。SDK 密钥不是 Harness admin API token；绝不把服务端密钥放入浏览器包。这些指标/事件工具不检索 SDK 密钥。获授权用户必须通过受支持的 UI/管理流程预配缺失的凭据。复用应用的配置模式；绝不硬编码密钥、请求粘贴的密钥、倾倒凭据文件或在工具/输出中暴露值。仅检查非机密配置元数据；标记环境不匹配以供确认，而不打印值。复用现有部署端点设置——不要推断自定义主机。

### 阶段 4：找到正确的位置

定位被跟踪动作实际完成的确切点（例如，在支付提供方成功确认购买之后，而非启动流程的按钮点击处）。错误的位置会产生误导性的指标数据，且没有错误可捕获。位置信号：相同动作的[现有应用分析调用](../../../references/fme/sdk-patterns.md#other-analytics-calls)、提交处理器、API 路由完成、mutation 成功回调、`TODO: track` 注释。现在确定候选 `file:line`；将调用批准推迟到完整事件契约已知之后（阶段 5–6）。确保事件每次预期结果只触发一次，而不是在重渲染、重试或客户端和服务端两者上再次触发。

**停止条件：** 如果有多个看似合理的位置（例如乐观 UI vs 服务端确认成功），询问用户哪个匹配指标意图，而不是猜测。

### 阶段 5：确认事件契约

事件名称区分大小写，必须与 `/create-metric` 使用过或将使用的完全匹配。如果指标已存在，**获取指标**并读取完整契约，而不仅是名称：`trafficType`、`aggregation`/`format`（决定值单位以及是否根本需要数值 `value`），以及值来自 `propertyForValue` 还是位置 `value` 参数，加上任何用于过滤器的必需 `properties`。如果指标尚不存在，现在与用户约定所有这些——不要推迟到阶段 6——以便 `/create-metric` 以后能引用同一契约而无不匹配。**在契约确定之前，不要起草或获取阶段 6 中 `track()` 调用的批准**；依据猜测的流量类型、聚合或值来源编写调用，与阶段 4 位置已避免的猜测是同一类问题。

对于现有指标，解析所选事件的确切 `eventTypeId`；如果它使用多个基础/过滤/触发事件，询问哪一个需要埋点。如果 RUM 或某个集成已覆盖此结果，在添加重复调用之前检查现有生产者和事件清单。仅清单可见性是历史证据，不是当前交付的证据——参见 [metric-design.md](../../../references/fme/metric-design.md#auto-created-metrics)。

### 阶段 6：编写并测试 `track()` 调用

使用阶段 5 契约展示候选 `file:line` 和确切调用，并**在编辑之前等待确认**。尊重已安装 SDK 的就绪生命周期和现有的初始化/包装器；不要为此事件创建第二个客户端。

使用 SDK 模式的签名，复用现有上下文对象（用户键、流量类型/属性）而不是构造新对象。服务端与客户端 `track()` 形状的示例见 [sdk-patterns.md](../../../references/fme/sdk-patterns.md)——然后对照已安装 SDK 的版本/类型或代码库中的现有调用来确认确切签名，因为该参考是伪代码，而非承诺的按语言规范。

Key = 与 `getTreatment` 使用的同一 key（归因事实）。值单位必须匹配阶段 5 契约中指标的 `format`（ms vs s、美元 vs 美分）——错误的单位会静默产生错误结果。`trafficType` 必须是指标的流量类型（阶段 5）。仅当契约要求时（`TOTAL`/`AVERAGE` 且无 `propertyForValue`）才传递数值；`COUNT`/`RATE`，或任何从属性读取的聚合，都不需要——不要为填充位置槽而臆造占位值。只要契约使用属性过滤器或 `propertyForValue`，就传递 `properties`。如果代码库已有跟踪包装器/辅助函数，扩展它而不是直接调用 SDK。

使用代码仓库既有的测试框架添加或更新聚焦测试：确切事件名称、评估主体键、流量类型、单位/值来源/属性、在预期结果上只触发一次、失败时无成功事件。在请求实时触发之前运行它们。Mock 的 `track()` 断言验证代码行为，**而非摄取**。

### 阶段 7：触发并验证

首先确认运行中的应用包含已编辑的修订并连接到预期环境；将修订/构建和环境记录为非机密元数据。如果它需要重启/构建/部署，请用户执行或授权该步骤——不要自动部署。没有它，停在“代码已测试；实时交付未验证”。约定一个能确立实际交付的获授权集成测试或运行时遥测来源；仅事件清单不能。

请用户触发该动作（或明确说明你无法自己执行他们运行中的应用），然后验证：使用确切事件名称**获取事件类型**。响应只有 `id` 和 `trafficTypes`——检查返回的 `trafficTypes` 包含指标的流量类型；错误流量类型下的命中不确认此事件。过去 30 天内有流量的事件类型（跨整个项目和所有环境，而非任何更窄意义上的“当前正在流动”）返回 200；404 = 不存在或闲置 > 30 天。

允许异步摄取。作为初步检查，大约每 30 秒重试一次，持续约 2 分钟；这是轮询启发式，不是交付保证。如果仍然缺失，报告交付未验证并调查，而不是宣布代码损坏。200 仅确认跨项目/环境的历史事件类型可见性，而非你的测试调用产生了它或到达了预期环境（没有按事件或按环境的查询）。

如果你检查的是与现有、先前工作的指标相关联的事件（而非全新测试），404 可能意味着“从未埋点”或“已埋点但闲置 30+ 天”，而不仅仅是“损坏”。在断定跟踪调用错误之前，先询问触发它的流程近期是否实际运行过。如果用户尚未实际触发该动作，结果是**未知**，而非“否”——不要报告你未观察到的否定。

大多数 SDK 会缓冲事件。对于短生命周期进程/测试，在退出前使用并等待已安装 SDK 支持的 flush/shutdown 行为。不要在长期运行的应用中逐事件 flush，也不要仅为强制交付而销毁共享客户端。

分开总结：(1) 事件名称/流量类型以及**在项目最近 30 天清单中可见：是/否/未知**，(2) **代码测试：通过/失败/未运行**，(3) **目标环境测试交付与实验归因：单独验证/未验证**，并指出证据。只有获授权的运行时遥测或真实集成检查才能验证交付；mock 测试和裸 200 不能。说明下一步（`/create-metric` 或 `/manage-experiments`）以及任何剩余的验证。

## 示例

- “为结账完成添加跟踪”——阶段 2-4 将调用放在支付确认之后，阶段 5 与 `/create-metric` 预期的 `checkout_completed` 约定事件名称，阶段 6-7 编写并验证。
- “注册事件真的在流动吗？”——仅跳到阶段 7，使用现有指标中已有的事件名称；如果缺失，在称之为损坏之前应用 30 天闲置的告诫。
- “为此服务接入新 SDK”——仅聚焦指标跟踪：阶段 2-3 为现有功能标志集成确认/安装 SDK（尚无 `track()` 调用）。不是首次功能标志门控设置——将代码门控路由到 `/instrument-feature-flag`，将端到端首次设置路由到 `/feature-flag-onboarding`。

## 性能注意事项

- 在假定没有 SDK 之前先检查现有 `track()` 模式——一个没有活动调用的部分/未使用 SDK 依赖与完全没有 SDK 是不同的情况。
- 不要在紧密循环中轮询**获取事件类型**——重试间隔见阶段 7（约 30 秒）。

## 故障排查

| 症状 | 原因 | 修复 |
|---------|-------|-----|
| 几分钟后事件仍不出现 | 确切大小写不匹配（事件类型名称区分大小写）；SDK 用错误环境的密钥初始化；进程退出前客户端未 flush/关闭；`track()` 调用中的流量类型与指标的 `trafficType` 不匹配 | 检查确切事件名称和流量类型；确认环境和凭据引用而不暴露值；检查就绪状态和 SDK 特定的关闭行为 |
| 无法判断我看到的事件来自我的测试还是其他流量 | 其他流量已在发送此事件 | 不要为一次性验证而重命名事件——它会创建第二个重复事件类型，并可能掩盖真正的命名不匹配。而是用 mock/自动化测试（阶段 6）验证约定的事件名称，并将实时 200 视为佐证而非证据 |
| 没有 SDK 且用户未说明语言/框架 | SDK 选择取决于代码库的语言和运行时（客户端 vs 服务端），而指标定义不编码这些 | 询问——不要从指标的流量类型或格式推断 SDK |
