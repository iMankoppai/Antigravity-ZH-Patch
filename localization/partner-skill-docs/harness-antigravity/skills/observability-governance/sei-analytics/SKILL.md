# SEI 分析

在 Harness Software Engineering Insights 中配置冲刺分析、投入分配、容量预测和发布就绪评估。

## 说明

### 步骤 1：确定范围

确认用户的 org、团队和跟踪周期。

```
Call MCP tool: harness_list
Parameters:
  resource_type: "project"
  org_id: "<organization>"
```

### 步骤 2：识别 SEI 任务

确定用户需要哪种分析：

1. **冲刺分析**——速度、估算准确性、范围变更跟踪
2. **投入分配**——按类别的工程时间细分
3. **冲刺规划与容量预测**——数据驱动的冲刺规划
4. **发布就绪评估**——发布 go/no-go 的检查清单

### 步骤 3：配置冲刺分析

从用户处收集：
- 团队名称和冲刺长度（周）
- 跟踪周期（最近 N 个冲刺）
- 问题跟踪器集成（Jira、Azure DevOps、Linear）

分析冲刺指标：

**速度：**
- 每个冲刺承诺 vs 完成的故事点
- 跟踪周期内的速度趋势
- 结转率（溢出到下一冲刺的故事百分比）

**估算准确性：**
- 跨冲刺的实际 vs 估算故事点
- 哪些问题类型一贯被低估
- 估算准确性趋势（改善或退化）

**范围变更：**
- 冲刺中途添加的故事（范围蔓延 %）
- 冲刺中途移除的故事
- 净范围变更及其对完成率的影响

**交付构成：**
- 按问题类型细分：功能、缺陷、技术债、维护
- 按优先级细分：P0/P1 vs 较低优先级
- 团队级 vs 个人级趋势

### 步骤 4：分析投入分配

从用户处收集：
- 要分析的团队
- 分析的时间段
- 投入类别（功能、缺陷、技术债、维护、运维）

计算分配：
- 每个类别的工程时间百分比
- 与目标分配比较（例如 70% 功能、15% 技术债、10% 缺陷、5% 运维）
- 随时间趋势：技术债在增长还是缩小？
- 按团队细分以识别在缺陷或运维上花费不成比例的团队

呈现：
- 当前分配 vs 目标分配
- 重新平衡的建议
- 当前分配对速度和质量趋势的影响

### 步骤 5：冲刺规划与容量预测

从用户处收集：
- 冲刺编号、时长和团队规模
- 计划中的 PTO、会议和其他承诺

计算容量：
- 可用工程天数 = 团队规模 * 冲刺天数 - PTO - 会议开销
- 每工程师每冲刺的历史速度
- 冲刺的推荐故事点（基于滚动平均值）

要标记的风险因素：
- 可能阻塞冲刺的大故事（>8 点）
- 对其他团队的依赖
- 来自前一冲刺的结转
- 可能拖慢功能工作的技术债项

### 步骤 6：发布就绪评估

从用户处收集：
- 服务名称、版本、目标环境
- 变更摘要和目标发布日期

评估就绪：
**代码质量：**
- 代码覆盖率差异（当前 vs 阈值）
- 静态分析发现（新警告或错误）
- 代码审查完成（所有 PR 已审查并批准）

**流水线健康：**
```
Call MCP tool: harness_list
Parameters:
  resource_type: "execution"
  org_id: "<organization>"
  project_id: "<project>"
```
- 发布分支的 CI 流水线通过率
- 所有必需阶段为绿（构建、测试、安全、集成）

**测试：**
- 单元测试通过率和覆盖率
- 集成测试结果
- 性能测试结果 vs 基线

**安全：**
- 无未解决的严重或高危 CVE
- 安全扫描已完成并批准
- 合规证明存在

**运维就绪：**
- 已为发布配置监控和告警
- 已为新功能更新运行手册
- 回滚计划已记录并测试

呈现为带 GO/NO-GO 建议的结构化就绪报告。

## 示例

- “显示平台团队的冲刺速度趋势”——分析最近 N 个冲刺的承诺 vs 完成点
- “我们的工程投入在功能与缺陷之间如何分配？”——计算投入分配并给出建议
- “根据我们的容量帮助规划 Sprint 24”——计算可用容量并推荐故事点承诺
- “checkout-service v2.1 准备好发布了吗？”——运行完整就绪评估并给出 go/no-go 建议
- “为什么我们的冲刺总是超额承诺？”——分析估算准确性和范围变更模式

## 性能注意事项

- 冲刺分析需要团队一致使用故事点——混合估算方法会降低准确性。
- 投入分配分析需要准确的问题标记——未标记的问题默认为 "unclassified" 并使结果偏差。
- 容量预测应考虑上下文切换开销（通常为工程时间的 10-20%）。
- 发布就绪评估应在计划发布日期前至少 24 小时运行。

## 故障排查

### 速度数据不一致
- 核实故事点在冲刺开始前分配（而非冲刺中途）
- 检查完成的故事在冲刺内标记为完成，而非之后
- 确保问题跟踪器集成正在正确同步

### 投入分配缺少类别
- 检查问题标记约定——所有问题都应有类型（功能、缺陷、技术债）
- 查看问题跟踪器标签与 SEI 类别之间的映射
- 为未标记问题添加默认分类规则

### 发布就绪检查不完整
- 核实发布分支的所有流水线阶段已运行
- 检查发布制品的安全扫描结果可用
- 确保监控配置已在 staging 中验证
