# 事故响应

使用 Harness MCP 将事故与部署关联、评估爆炸半径并生成复盘文档。

## 说明

### 步骤 1：确定范围

确认受影响的服务、环境和事故详情。

```
Call MCP tool: harness_list
Parameters:
  resource_type: "service"
  org_id: "<organization>"
  project_id: "<project>"
```

### 步骤 2：识别事故响应任务

确定用户需要哪个工作流：

1. **部署到事故关联**——确定近期部署是否导致了事故
2. **爆炸半径评估**——映射受影响的服务和下游影响
3. **复盘生成**——创建结构化的复盘文档

### 步骤 3：将部署与事故关联

从用户处收集：
- 受影响的服务名称和环境
- 告警或事故名称及开始时间
- 观察到的症状（错误率突增、延迟、中断）

拉取近期部署：

```
Call MCP tool: harness_list
Parameters:
  resource_type: "execution"
  org_id: "<organization>"
  project_id: "<project>"
  status: "Success"
```

对于每次近期部署，检查：
- **时间：** 部署是否在事故关联窗口内（例如事故前 2 小时）？
- **服务匹配：** 部署的服务是否匹配或依赖于受影响的服务？
- **变更内容：** 部署中更改了什么（配置、代码、基础设施）？

构建部署时间线：
1. 列出过去 N 小时内到受影响环境的所有部署
2. 在时间线上标出事故开始时间
3. 识别最可能的因果部署（事故开始前最近的）
4. 检查是否执行了回滚以及是否解决了问题

以置信度呈现发现：HIGH（部署匹配时间 + 服务）、MEDIUM（时间匹配但服务不同）、LOW（未发现部署关联）。

### 步骤 4：评估爆炸半径

从用户处收集：
- 失败的服务和故障类型（中断、错误率升高、高延迟）
- 当前错误率或严重性
- 环境

映射影响：

```
Call MCP tool: harness_status
Parameters:
  org_id: "<organization>"
  project_id: "<project>"
```

评估：
- **直接影响：** 失败服务的错误率、延迟和可用性
- **上游调用方：** 调用失败服务的服务——它们是否在退化？
- **下游依赖：** 失败服务所依赖的服务——它们是否健康？
- **用户影响：** 根据流量估算受影响的用户
- **数据完整性：** 是否存在数据损坏或不一致的风险？

对严重性分类：
- **Critical：** 面向用户的中断、数据丢失风险，或多个服务受影响
- **Major：** 影响用户的性能退化，单个服务受影响
- **Minor：** 内部服务退化，无面向用户影响

根据爆炸半径建议立即行动：
- 如果与部署关联：建议回滚并给出预期解决时间
- 如果与基础设施相关：建议故障转移或扩缩容
- 如果与依赖相关：建议激活熔断或优雅降级

### 步骤 5：生成复盘

从用户处收集：
- 服务名称和事故摘要
- 事故时长和环境
- 已采取的解决步骤

构建复盘结构：

**1. 执行摘要**——发生了什么、客户影响、时长（2-3 句）

**2. 时间线**——从 Harness 流水线事件和告警时间戳构建：
- 问题首次检测到是什么时候？
- 值班团队何时介入？
- 什么部署或变更触发了回退？
- 缓解何时应用、服务何时恢复？

拉取时间线数据：
```
Call MCP tool: harness_list
Parameters:
  resource_type: "execution"
  org_id: "<organization>"
  project_id: "<project>"
```

**3. 根因分析**——哪个部署或变更触发了事故以及为什么

**4. 影响评估**——受影响的服务、环境和大致用户影响

**5. 行动项**——分类为：
- 立即修复（解决根因）
- 流程改进（防止复发）
- 监控改进（更快检测）

**6. 经验教训**——哪些做得好、哪些不好、哪些靠运气

## 示例

- “我们的支付服务宕了——是部署导致的吗？”——将事故与近期部署关联并提供置信度
- “checkout 中断的爆炸半径是什么？”——映射上游/下游服务并估算用户影响
- “为昨天的 auth-service 事故生成复盘”——创建带时间线、RCA 和行动项的结构化复盘
- “刚触发了一个 Sev-1——是哪次部署导致的？”——拉取近期部署并与告警时间关联

## 性能注意事项

- 部署关联在 2 小时窗口内最准确——超过后，其他因素变得更可能。
- 爆炸半径评估需要最新的服务依赖映射——过期的映射会漏掉连接。
- 复盘应在 48 小时内生成，此时事故在团队记忆中仍新鲜。
- 复盘始终包含做得好的地方——无责文化需要肯定良好的响应。

## 故障排查

### 关联窗口内未找到部署
- 将搜索窗口扩大到 4-6 小时——部分故障有延迟发作
- 检查基础设施变更（不仅仅是代码部署）
- 查找配置变更、功能标志切换或证书过期

### 爆炸半径评估缺少服务
- 服务依赖映射可能不完整——检查未记录的依赖
- 查找多个服务共享的基础设施（数据库、消息队列）
- 检查外部依赖（第三方 API、DNS、CDN）

### 复盘缺少时间线事件
- 从多个来源拉取：流水线执行、告警历史和聊天记录
- 检查是否发生了可能不在部署历史中的自动回滚
- 在部署事件之外包含基础设施事件（自动扩缩、节点故障）
