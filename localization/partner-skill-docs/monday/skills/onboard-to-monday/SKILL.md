# 引导上手 monday.com

在一次简短的对话中，让一位全新的 monday.com 用户从“刚刚连接”变成拥有一个他们认作自己的、可用的看板。目标是在几分钟内取得第一次成功：一个围绕用户真实工作构建的看板，带有真实条目、一个自动化，以及一个明确的下一步操作。

看板本身由 `create_board` 配合 `creationPrompt` 构建——monday 根据自由文本描述设计分组与列。本技能决定*要请求什么*，然后检查结果并填补任何缺口。关于列值格式与写入失败处理，请使用 **task-management** 技能。

## 原则

- **先提议，后询问。** 不要一上来就发问卷。根据你已知的信息起草一个设置，然后问一个确认问题。
- **对你推断的内容保持透明。** 说明你的提议依据什么，以便用户纠正。
- **仅使用工作上下文。** 使用用户的角色、团队、公司、当前项目与工具。绝不要把个人或敏感细节（健康、家庭、财务、私人对话）放进创建提示词、看板名称、条目或描述中。
- **快速。** 争取一次确认、一次构建、一次首次操作。使用明智的默认值并说明它们；不要询问有合理默认值的事情。

## 工作流

### 步骤 1：确认这是新用户

调用 `get_user_context`。

- 用一行告诉用户他们连接到哪个账户与工作区。
- **新用户**（试用或最近创建的账户，自有看板很少或没有）：继续步骤 2。
- **现有用户**（该账户已有他们在用的看板）：不要运行引导。说明他们已有设置好的看板，说出几个最相关的看板名称，并提出改为帮助处理那些（状态更新、添加条目、新看板）。
- **意外的账户**（用户说不是正确的那个，或预期的看板缺失）：停下来，请他们断开并重新连接 monday.com 连接器，选择正确的账户。

记下套餐层级与试用状态，供步骤 6 使用。

### 步骤 2：勾勒用户的工作

使用你从本次对话以及（若有）更早的对话或记忆中所了解的关于用户的信息：他们的角色、团队、公司或行业，以及他们当前在做的事（项目、发布、客户、招聘、活动）。

- **如果你了解得足够多**，能猜出他们会跟踪什么，直接进入步骤 3。
- **如果你了解得很少或一无所知**，用一条消息最多问三个简短的问题：
  1. 你想在这里管理什么样的工作？（例如项目、客户/交易、内容、请求、招聘、某个活动）
  2. 你现在正在做的一件真实的事是什么？
  3. 这只是给你自己用，还是给一个团队用？

### 步骤 3：提议一个量身定制的设置

确定：

- **看板名称**取自他们的真实工作（例如“Q4 Product Launch”、“Acme Client Pipeline”），而不是“My Board”。
- **看板跟踪什么以及工作如何流转**（阶段、每个条目的关键字段——负责人、截止日期、优先级、价值等）。
- **3-5 个取自他们实际工作的起始条目**——你所知或他们刚提到的真实里程碑、客户或任务——绝不用“Task 1”。把截止日期分散在未来两周内。
- **一个起始自动化**（见下文“起始自动化”）。

紧凑地呈现它，并问一个问题，例如：

> 根据我所了解的——你在 Acme 领导市场团队，正在规划 Q4 发布——我会设置一个 **Q4 Launch Tracker**，让每个发布任务经过 To Do / In Progress / In Review / Done 流转，带负责人、截止日期与优先级，从这些开始：Finalize messaging、Launch landing page、Partner email、Launch day checklist——外加一个在任务卡住时通知负责人的自动化。要不要我构建它，还是先改点什么？

如果他们改了某些内容，就调整并构建。小幅更改之后不要再次确认。

### 步骤 4：创建看板

1. **检查名称冲突。** 用看板名称调用 `search`。如果存在同名看板，询问是使用它，还是用不同的名称创建新看板。
2. **调用 `create_board`**，传入 `boardName`、`boardKind: "public"`（若用户要求则为 `"private"`）、步骤 1 的工作区，以及一个用平实语言描述该看板的 `creationPrompt`：它跟踪什么、工作流阶段、每个条目需要的字段，以及起始条目。把自动化排除在外——它不是从提示词创建的；步骤 6 会添加它。根据商定的提议编写提示词，例如：

   > 一个供市场团队规划 Q4 产品发布使用的发布跟踪器。工作经过 To Do、In Progress、In Review、Done 流转。每个任务需要负责人、截止日期与优先级（Low、Medium、High、Critical）。起始任务：Finalize messaging、Launch landing page、Partner email、Launch day checklist。

3. **如果 `create_board` 失败或超时，不要立刻再次调用它**——看板可能已被创建。先按看板名称调用 `search`，只有它不存在时才重试。重发会创建重复的看板。

### 步骤 5：检查结果、填补缺口并展示看板

`creationPrompt` 能让看板大部分正确，但并非全部。调用 `get_board_info`、`get_board_items_page`（`includeColumns: true`）与 `list_automations`，并与你所提议的进行比较：

- **分组顺序**——如果较晚或终止性分组（例如“Done”）在最上面，新条目会落到那里。用 `all_monday_api` 把第一个工作流阶段移到顶部：`update_group(board_id, group_id, group_attribute: relative_position_before, new_value: "<current top group id>") { id }`。
- **列**——如果缺少某个关键字段或类型错误（例如网站是 `text` 而不是 `link`），用 `create_column` 添加它。不要重建看板。
- **条目**——如果缺少起始条目，在一次 `create_items` 调用中创建它们；如果你请求的值是空白的，在一次 `update_items` 调用中填写它们。遵循 task-management 的列格式。仅在他们同意时才把条目分配给当前用户。
- **未被请求的自动化**——`create_board` 可能添加没人要求的自动化（例如使用 AI 额度的 monday AI“分类”规则）。用一行提及它们，并提出可以关闭它们。

如果写入工具在成功读取之后失败，请遵循 task-management 规则：重试一次，然后停下来并请用户重新连接连接器。不要不断重建。

**立即展示看板。** 一旦列与起始条目就位，就用新看板的 `boardId` 调用 `show-table`，以便用户在聊天中看到他们的看板作为交互式表格。不要传 `filters`；展示整个看板。加一句简短的话，例如“这是你的看板——接下来添加一个起始自动化。”不要等自动化步骤。如果 `show-table` 不可用或失败，则改为分享工具响应中的看板 URL 并继续。

### 步骤 6：添加起始自动化

创建之前先询问（它可以是步骤 3 确认的一部分）。

1. 用 `boardId` 与一个以用户术语表述的结构化描述（触发器 / 条件 / 操作）调用 `create_automation`，使用步骤 5 中的真实列名与分组名。如果它返回 `needs_clarification`，询问缺失的细节并再次调用它。
2. **回读它。** 为该看板调用 `list_automations`，检查触发器与条件是否匹配请求——尤其是“状态变为 X”的触发器是否也不要求之前的状态为 X，以及条件是否未被反转。如果错了，用 `manage_automations`（`action: "deactivate"`）停用它并重新创建。
3. 如果 `manage_automations` 对你刚创建的自动化返回 `USER_UNAUTHORIZED`，不要重试——告诉用户从看板的 Automations 面板关闭它。
4. 如果 `create_automation` 因套餐或试用被拒绝，跳过它，提及自动化在付费套餐中可用，并继续。不要让这一点阻塞看板。

### 步骤 7：以一次首次成功交接

看板已在步骤 5 显示在屏幕上——不要在此处再次调用 `show-table`。

1. **用几行总结：** 构建了什么、自动化（若已创建）以及工具响应中的看板 URL。不要把条目作为文本列表重复——表格已展示它们。（如果步骤 5 中 `show-table` 失败，则在此处列出起始条目。）
2. **给出一件现在就能尝试的具体事情，** 措辞为他们可以直接说出的话，使用他们自己的某个条目：
   - “试试：说 **mark Finalize messaging as done**。”

   当他们这么做时，执行该更改（task-management 技能），然后再次调用 `show-table`，让他们看到看板更新。

然后简要提供能让人回访的习惯：

- “随时问我这个看板上 **what's overdue** 或 **give me a status update**。”
- “要我邀请你的队友，让他们能和你一起处理这个吗？”（仅当他们说过这是给团队用时）

到此为止。除非用户要求，不要继续串联更多设置。

## 起始自动化

选择契合该看板的那个，使用其真实的列、标签与分组名称：

| 看板类型 | 起始自动化 |
|---|---|
| 项目 / 任务 / 冲刺 | 当 Status 变为 Done 时，把该条目移到 Done 分组 |
| 客户 / 交易 / CRM | 当 Stage 变为 Closed Won 时，把该条目移到 Closed Won 分组 |
| 内容 | 当发布日期到达时，通知作者 |
| 请求 / 受理 | 当创建新条目时，通知受派人 |
| Bug / 问题 | 当 Severity 变为 Critical 时，通知受派人 |
| 活动 / 其他 | 当 Status 变为 Stuck 时，通知负责人 |

## 使用的工具

- `get_user_context` —— 账户、工作区、套餐与试用状态，以及用户是否已有看板
- `search` —— 看板名称冲突检查，以及检查失败的 `create_board` 是否实际创建了看板
- `create_board` —— 根据 `creationPrompt` 构建看板
- `get_board_info` —— 回读生成的列、分组与标签
- `get_board_items_page` —— 检查起始条目的值
- `all_monday_api` —— 当第一个阶段不在顶部时重新排列分组（`update_group`）
- `update_items` —— 填写生成的看板留空的起始条目值
- `create_column` —— 添加生成的看板缺少的关键列
- `create_items` —— 如果生成的看板没有起始条目，则添加它们
- `create_automation` —— 创建起始自动化
- `list_automations` —— 验证自动化的触发器与条件
- `manage_automations` —— 停用创建错误的自动化
- `show-table` —— 一旦新看板的条目存在就展示它（步骤 5），并在用户做出首次更改后再次展示
