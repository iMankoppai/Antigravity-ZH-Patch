# Postman MCP Server

MCP 把工作区资源直接暴露给智能体。现有的集合、
规范、示例与环境提供已维护的 API 知识；在本地 CLI 工作流不可用时，
获取相关实体可保留该上下文。对于代码仓库编辑与 Git 审查，在可用时
优先使用 **api-engineer** 与 **bootstrap** 中的本地工作流。

暴露给模型的每个工具定义，只要被包含在请求中就会消耗上下文。
优先使用覆盖任务的最小可用工具集；扩展到每一个工具可能会挤掉
推理所需的 API 证据。当被暴露时，在诊断缺失操作之前调用 `getEnabledTools`
检查活动工具集。否则使用宿主机已发现的工具并
报告该限制。不要根据参考中的工具名称推断可用性，也不要
假定某个客户端可以切换一条固定到特定 MCP 端点的路由。

1. 从已连接服务器的实际接口中选择工具。工具可用性
   因模式而异；参考中列出的名称并不能证明它已被暴露。
   连接/鉴权失败请使用 [setup](references/setup.md)，当操作缺失
   或行为与 CLI 不同时使用 [limitations](references/mcp-limitations.md)。
2. 先搜索定位实体，再获取足够的细节以便处理它。
   `searchPostmanElements` 找到候选；集合、规范与工作区
   详情工具确立 ID、归属与内容。搜索预览对于替换集合
   或宣告 API 不存在而言是不充分的证据。
3. 让变更与预期范围相匹配。请求级更新保留
   无关的集合内容；整集合替换需要
   当前的完整对象。工作区是一个容器与访问边界，
   而不是每当新任务开始就创建重复资源的理由。
4. 同步时保留权威来源。规范到集合的
   生成复用接口，而集合到规范的同步携带
   另一方向的变更。根据预期的契约选择，
   而不是覆盖最容易触及的那个产物。异步
   接受响应需要已完成的任务结果才能声称同步成功。
5. 把发布与编辑分开看待。集合示例可以供给
   文档与一个 classic mock，但二者都不会仅仅因为存在
   就变为公开可访问。在发布文档或 mock，或更改共享资源之前，
   应用用户预期的受众与授权。

## 验证

说明通过 `getEnabledTools` 观察到的活动工具集，或当该工具不可用时
指出所使用的宿主机发现证据。报告已连接接口无法执行的任何操作，
而不是声称它已成功。

报告资源与观察到的结果：一次运行的断言、生成产物的已完成同步，
或发布的可达 URL 与可见性。仅工具成功并不能确立其中任何
结果。
