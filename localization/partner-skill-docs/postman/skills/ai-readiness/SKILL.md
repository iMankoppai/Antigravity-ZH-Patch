# AI 就绪度

智能体必须选择操作、提供有效输入，并从它所能看到的契约中解读失败。
Postman 的就绪检查会暴露该上下文中的缺口——例如缺少示例或参数含义不清——
于是改进落在共享契约上，而不是在每个智能体会话中重新发现。

对于拼写修正、一次性端点检查，或者既不改变契约也不改变智能体可用性的任务，
请跳过评分；改为检查相关字段或使用 **api-testing**。当需要优先改进可消费性、
检查其效果，或执行约定的就绪门槛时，才进行评分。

1. 对消费者实际使用的产物评分。`postman collection ai-readiness
   <path-or-id>` 读取一个集合，包括本地 v3 目录；
   `postman spec ai-readiness <path-or-id>` 直接读取 OpenAPI 规范。
   仅为给规范评分而生成集合，会增加第二个产物却不会改善证据。使用已安装命令的 `-h` 查看选项。
2. 使用报告的 `readiness` 分数与分档（Limited、Fair、Good、
   Excellent）。将 `confidence` 单独看待：低置信度意味着信号无法被测量，
   因此即使分数很高，也可能遗留重大的未知项。
   当标记低文档覆盖率时请报告；它会修正分数，
   而不是充当独立的通过/失败门槛。
3. 优先处理会改变调用方行为的缺口：不清晰的必填输入、
   缺少鉴权说明，或没有恢复指引的错误。
   在添加描述或示例之前，先确定实际行为；
   臆造的确定性会提高表面完整度，却误导智能体。
   改进权威契约见 **api-documentation**，已保存示例见
   **collection-schema-v3**。
4. 对编辑后的产物重新运行，以显示哪些测量差距已闭合。
   就绪分数衡量的是可消费性，而非实时正确性；当结论还取决于 API 行为时，
   请使用 **api-testing**。
5. 当团队希望防止就绪度回退时，`--min-score` 门槛很有用。根据基线与预期选择阈值；
   通过 **ci-integration** 将其与测试、lint 分开，使失败能
   指明是哪一种回退。

## 验证

报告目标、collection/spec 模式、实际分数、分档、置信度
以及剩余差距。如果运行了阈值，请包含其退出码；仅凭一次成功的
扫描并不足以证明阈值已通过。
