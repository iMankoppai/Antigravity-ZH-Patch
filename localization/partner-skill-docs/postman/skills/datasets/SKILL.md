# 数据集

数据集为文件与数据库来源提供一个可查询的接口；已保存视图
把查询变成可复用的测试输入。当过滤、
连接或刷新行是测试的一部分时，这很有用。一次性的 CSV/JSON 运行可以
继续用 `collection run -d`；数据集应凭其额外配置证明自身价值。

## 选择数据与执行路径

1. 对于可复现的固定数据，优先使用本地文件来源。当当前数据本身
   就是目的时，实时数据库很有用，但即使在本地 `.dataset.yaml` 中也会增加鉴权、权限、
   网络与凭据要求。
   在承诺某个工作流之前，检查 `postman dataset <action> -h` 与实际来源能力；
   来源支持可能随已安装的 CLI 而变化。
2. 使用默认的联邦 SQLite 查询路径来连接受支持的来源。
   `--source <name>` 则用某来源的原生方言向其发送 SQL。
   为了压住一个 SQL 错误而切换模式，会改变查询语义。JDBC
   需要原生路径，无法在联邦层连接；原生
   数据库连接器可以支持联邦。
3. 在选择数据库连接器之前先选择凭据。JDBC 变量
   与属性接受共享保险库引用，例如
   `vault:<vaultId>/<secretId>`，在查询时解析。原生数据库
   凭据在文档所述的 CLI 表面上以字面值存储在数据集配置中；
   使用前先检查当前支持，并让含机密的
   配置远离 Git。通过 stdin 传入的字面值可避免在 argv
   中暴露，但仍可能被持久化到 YAML。关于保险库
   处理见 **variables**。启用连接的连接器可能具有比 JDBC 更差的凭据
   边界；不要掩盖这一取舍。
4. 有意识地选择迭代或脚本访问。成对的
   `--iteration-data-dataset <path-or-id>` 与
   `--iteration-data-view <name-or-id>` 标志为每次集合迭代
   供给一行，列以变量形式暴露。它们排除 `-d`，并且需要
   一个无参数的视图，因为 runner 没有查询参数输入。
   可重复的 `--dataset <path-or-dir>` 则把 `pm.datasets()` 暴露给
   脚本；它本身并不创建由行驱动的迭代。

## 构建可移植、可查询的产物

用 `postman dataset create <path.dataset.yaml>
--name <name>` 创建本地清单，然后用 `dataset source add` 附加来源。来源命令
提供手写条目可能遗漏的 ID 与校验。现有数据集的
命令接受本地路径或工作区 ID；`list` 需要本地路径才能
本地发现，而工作区 create/list 使用 `--workspace`。

除非使用 `--ref-only`，文件来源会被复制到 `data_dir` 中。该选项
记录绝对路径，使数据集与机器相关。对于工作区
数据集，单独添加 `--file` 只是注册一个本地文件系统来源；`--upload`
才会真正上传字节。发布整个项目时请使用 **bootstrap** 的工作区同步；
没有单独的 `dataset push`。

对于电子表格来源，使用
[电子表格来源](reference/spreadsheets.md) 中感知工作表的指引。对于普通来源名称，
优先使用规范化标识符：表名小写，折叠重复的
下划线，并去除边缘下划线。名为 `users` 的来源查询时
为 `users`，而不是 `source_users`。在把未知表错误解读为缺失数据之前，
请先核实实际的表。

对于 JDBC，`dataset jdbc inspect <driver.jar>` 提供驱动类、URL
模板、变量与属性，供 `source add` 使用；`--from-source` 可以复用
连接。除非禁用，JDBC 添加会测试连通性；原生来源
添加需要单独的 `dataset source test`。这一区分防止
把已保存来源误认为可用的连接。

在保存之前用 `dataset query` 证明查询可用，然后再用 `dataset view create`
保存，然后运行该视图。查询参数是位置式的（`$1`、`$2`，配合 `-p`
按顺序传值）。提交清单与预期来源文件；把引擎
状态（如 `data.db`、`meta.db`、`daemon.log` 与缓存）留在代码仓库之外。
数据集命令不会创建 `.postman/resources.yaml` 注册表条目。
删除会移除清单，但保留可能共享的来源文件。
删除工作区数据集是永久的；请先确立该意图，而不是
把删除当作修复查询的手段。

## 解读失败与结果

通用的服务器错误包装可能掩盖 SQL 或连接错误。使用结构化的
`--json` 错误及其补救措施，或必要时用 `--debug`，在重试之前识别
出问题的层。`source test` 把数据库连通性与
SQL 错误区分开；文件/URL 来源没有可测试的连接。引擎启动失败
可能需要查看 `data_dir` 的守护进程日志，而不是换一个查询。

脚本的数据集访问是惰性的，无效 YAML 可能被跳过并给出警告，
而不是让运行失败。在托管集合上，`--dataset` 并非
访问控制边界：脚本可以访问该会话可读的其他数据集。
在运行不可信脚本之前，用该会话检查集合的数据访问权限。

## 验证

报告被查询的列与行数、本地/工作区位置、实时与
复制来源，以及联邦与原生执行。对于迭代运行，
把实际迭代次数与预期视图行数及配置的
限制进行比较。数量相符只确立了接线，而非数据覆盖了测试所需的每一种
行为。仅创建清单两者皆不能证明。
