# Webhook 测试

`postman webhook` 给发送方一个托管 URL，
`https://<webhookId>.webhook.pstmn.io`，它记录收到的每个请求，
保留发送时的原始请求头与请求体，并把每个请求转发到
本机的一个端口。你无需单独的隧道。有两个特性会影响
如何使用它：

- **跨调试会话复用 URL。** 它能在新会话、暂停
  与启动之间存活，因此发送方只需注册一次。当用户指定某个 webhook、
  或说发送方已向某个 webhook 投递时，请复用它。使用 `list` 来解析该
  引用；仅当可用上下文仍留下多个可能选项时才询问。
  当需要新端点时，才创建新的。每个新 webhook 都是另一个
  需注册的 URL 与第二份事件历史。
- **每个请求都被记录，** 包括在没有任何东西转发时到达的请求。
  `requests describe` 显示一次投递发送时的精确样子。
  修复之后，`requests replay` 会再次发送它，因此你无需让发送方
  再触发一次。

该命令是单数形式，且每个子命令都需要已登录的会话。按需运行，
仅当命令因设置错误（如 `Authentication required`）失败时才阅读 `bootstrap`。
当你只有 URL 时，其子域就是 webhook id。

若仅为捕获或检查，创建或复用一个 webhook 并检查其
记录的请求即可；无需本地服务或转发到本地端口。

使用重放与[脚本](reference/webhook_scripts.md)来验证入站事件。

## 让发送方到达 localhost

当任务是到达某个本地处理器时，检查从打算转发到本地服务的公开 URL
出发的路径：

1. **确保路由存在。** 一个转发到本地服务却无匹配路由的 URL
   只会返回 404。检查本地服务是否有针对此事件的
   处理器。当实现接收方是任务的一部分时，补上缺失的处理器。
   发送方会重试，且重放会重发一个相同的请求，因此在可用时使用
   发送方稳定的事件标识符去重。
   对于处理器有意忽略的有效、已鉴权事件，用 2xx 予以确认，
   以避免不必要的重试；格式错误或
   未鉴权的请求仍需拒绝。
2. **复用现有 webhook 或创建新端点。** 要创建一个，使用
   `postman webhook create --title <name>`。当显然需要新端点时，
   直接创建它可避免不必要的发现步骤。
3. **启动本地服务，然后转发到其端口，** 使用
   `postman webhook forward <webhookId> <port>`。`forward` 会一直运行直到被
   停止，因此在后台运行它。关于停止转发进程，
   见 [转发生命周期](reference/forwarding.md)。
4. **向该 URL 的路由路径发送一个请求。** 检查是否返回了 2xx，
   以及处理器是否记录了该请求。`requests list` 显示请求是否
   到达了 webhook，从而把错误的 URL 与转发或路由问题区分开。

对于连通性任务，一次成功的探测证明所测试的
路径到达了处理器。发送方兼容性与处理器正确性则需
来自实际发送方投递与相关场景的证据。

## 注意事项 / 说明

- **根据发送方的契约构建 webhook 脚本的测试事件，而不是根据你的处理器。**
  为匹配你刚写的处理器而编写的载荷，只能证明二者
  彼此一致。请从发送方文档化的事件 schema 取用。
  更好的做法是使用一次真实投递：从发送方的测试模式发送一个（例如
  `stripe trigger <event>` 或 GitHub 重新投递），然后在你迭代时重放那个已记录的
  请求。
- **权限错误需要工作区上下文。** 检查所选的工作区
  与账户的访问权限。一个克隆的代码仓库可能指向此
  账户无法使用的工作区。如果已知预期可访问的工作区，请传入
  `-w`；否则询问使用哪个工作区。创建另一个工作区
  并不会授予对现有工作区的访问权限。
- **某些旧的已签名事件在重放时按设计会验证失败。** Stripe
  （`Stripe-Signature` 中的 `t=`）与 Slack（`X-Slack-Request-Timestamp`）对
  时间戳签名，其 SDK 会拒绝早于约五分钟的请求。
  请改为发送一个新事件，而不是放宽验证。GitHub 的签名没有
  时间戳，因此其重放仍能通过验证。
- **在 `delete` 之前确认。** 它是永久的，且仍注册到
  该 URL 的发送方会开始失败。重放也会到达应用代码，因此在选择重发哪次
  投递时，请考虑处理器的副作用。

## 交接

对于端点设置，让 webhook 保持活动，以便用户能把发送方
指向它。对于已完成的调查，根据发送方是否仍需该端点来选择
最终状态。当 `forward` 进程结束时转发即停止；只要 webhook 保持活动，
到达会被记录并
可被重放。向用户提供：

- 带路由路径的 URL；
- 对于本地转发，重启循环的两个命令：启动
  本地服务，然后 `postman webhook forward <webhookId> <port>`；
- 对本地服务所做的任何更改；
- 已验证了什么：对于转发测试，是捕获的投递，还是响应与处理器收到记录。

要用 `pm.test` 脚本自动验证投递，见
[reference/webhook_scripts.md](reference/webhook_scripts.md)。要测试你自己的 API 发出的
webhook（以 Postman webhook 作为订阅者），见
[reference/outbound_webhooks.md](reference/outbound_webhooks.md)。
