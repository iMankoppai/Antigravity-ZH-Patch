# API 监控

监控器把已保存的集合变成关于实时 API 的周期性证据。
它能捕捉部署之后或开发者会话之间发生变化的行为，但前提是其断言、环境与执行位置
确实检验了用户所依赖的保证。

1. 在安排计划之前，复用集合中有意义的断言。一个
   返回 200 的请求，如果响应可能违反
   契约，那它就是个弱的健康信号。检查鉴权、目标环境与写入副作用；使用
   **api-testing** 来确定集合实际验证了什么。
2. 根据运维需要选择频率、时区、执行位置与告警接收人。
   `postman monitor create -c <collection-id>` 默认使用
   已链接的工作区，除非另外指定。查看命令专属的
   `-h` 与可用的服务选项，了解支持的计划与限制。
   创建时默认会立即启动一次运行；当只请求安排计划时，`--no-run-now` 可避免这一点。
   以宿主机默认时区表示的计划可能会在错误的运维时间触发。
3. 对于可访问的公共 API，选择 Postman 区域。当目标只能在用户网络内部
   访问时，使用自托管 runner；
   运行它会增加需要维护的基础设施。`postman runner regions`
   提供有效的托管位置，`runner list` 提供已注册的
   私有 runner ID。`monitor create/update --runner` 接受二者之一；
   多个位置有助于区分 API 失败与区域性可达性问题。
4. 在更新计划或运行设置时，保留监控器身份。
   `monitor update` 不能更改其集合或环境，也不会
   暂停它；请使用 `pause`/`resume` 来做这些。不同的集合/环境
   需要一次替换，因此在删除旧监控器及其连续性之前，请先规划好交接。
   永久删除需要明确的意图。
5. 使用 `postman monitor run <id>` 获取即时判定，例如在
   部署之后。当调用方无需等待时，`--async` 返回一个任务句柄。
   CLI 超时限制的是等待时间，而非执行；超时之后，请检查
   已提交的任务，而不是发送重复流量或报告失败。
6. 在证据的层面进行诊断。`monitor jobs list <monitor-id>`
   查找任务，`monitor jobs get <job-id>` 显示终止状态与区域
   结果，`monitor runs get <run-id>` 显示单次尝试中的
   断言。某个区域失败、连接错误与断言失败
   意味着不同的修复方式。为 CI 门槛保留正常的退出码失败。

关于发现，`monitor list` 支持工作区与集合过滤；
请使用其返回的游标进行分页，而不是用 offset。其 runner 过滤
用于自托管 ID，不能与其他过滤条件组合；一个页内
名称过滤并不能证明在所有页中都不存在。

对于私有 runner，使用 `runner start` 传入已注册的 ID 与 key，并在分配运行之前
确认它已连接。仅当网络需要时，才查看其帮助中的代理、
私有 CA、驻留与健康指标选项。Runner 活动默认会被报告；当任务需要时，`--no-report-events` 可禁用
该报告。对于未解决的鉴权问题，请使用 **bootstrap**，而不是把 runner key 放进代码仓库文件。

## 验证

报告实际的监控器配置或终止的任务/运行结果，包括
它在哪里执行以及哪些检查失败。一个已创建的监控器、已接受的任务
或已连接的 runner 本身，并不能证明该 API 通过了其健康检查。
