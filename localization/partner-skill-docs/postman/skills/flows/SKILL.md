# Postman Flows

一个 Flow 把 API 工作流保存为一张块组成的图。命名输入让运行
可重复，部署让工作流可被其他系统调用，块级运行证据显示它在哪里失败。
这些好处来自不同的执行路径；选择错误的路径可能产生一个通过的
结果，却对调用方的实际工作流毫无说明。

1. 选择用户所指的产物。`postman flows run <path>` 执行一个
   本地 JSON 文件；`postman flows trigger <flow-id>` 调用已部署的
   webhook，包括触发鉴权与配置。本地 View 与 Cloud
   View 产物是隔离的：不能假定本地文件可部署，
   且 `workspace pull` 不会下载它们。桌面应用中已连接 Git 的 Local View
   会生成那些文件。围绕它构建 CI 之前，先检查当前的本地运行权限；
   已部署的 flow 并不能替代另一个本地产物。
2. 通过 `flows list --workspace <id>` 解析托管 ID；`.postman/resources.yaml` 中没有
   本地 flow 映射。适用时复用其 `workspace.id`，或使用 **api-discovery** 进行
   跨工作区搜索。在改动 flow 之前先解析有歧义的名称。原样使用返回的 flow/run ID；
   它们的拼写不是可靠的校验规则。
3. 当同一载荷应随 flow 一起传递时，复用 Start 块的场景。
   `-s` 提供载荷、请求头与查询；显式请求头/查询与
   `-i`/`-f` 覆盖那些值。一次性输入应放在调用上。
   对于有副作用的已部署 flow，`trigger --dry-run` 让你先检查
   解析后的调用；保持机密遮蔽。
4. 当工作流需要一个可调用的 URL 时进行部署。托管 flow 需要
   为 API 请求触发器配置的 Start 块，以及一个 Response 块；
   更改 CLI 标志无法修复缺失的画布配置。部署前
   先解析路径后缀与预期的鉴权。部署/鉴权
   变更会影响其他调用方；限定的用户请求即为该变更授权，
   而未被请求的公开暴露或移除鉴权则需要同意。
5. 检查已部署的 URL 及其触发器是否已启用。一个已部署
   但被禁用的 flow 尚未准备好接收调用；在需要时，`flows update <id>
   --trigger on` 会启用它。如果部署是所请求运行的一部分，
   请继续触发并捕获 Run ID。仅为部署的请求
   并不授权执行无关的下游写入。
6. 从运行证据进行诊断。触发响应是 Response 块的
   输出：HTTP 200 可以与其他块失败并存。使用
   `flows get-run --run-id <id>`，当摘要不足以解释时添加 `--logs` 或块过滤。
   `flows list-runs --workspace <id> --flow <id>`
   可找回缺失的 run ID；在断言不存在之前先放宽其时间范围。
7. 在 CI 中，保留本地运行的失败退出码并持久化其结果
   与报告。连接器块即使对本地文件也需要 `--workspace`；
   否则失败会发生在图内部。跨多个
   工作区的访问拒绝指向凭据或权限，而非空的 flow 列表。
   未解决的 CLI/鉴权初始化请使用 **bootstrap**。

阅读 [命令选项](reference/flow_cli_flags.md) 了解输入、报告器、
数据集迭代与标志冲突；在命令之间沿用某个选项之前，先检查已安装子命令的 `-h`。

## 验证

报告执行了哪个产物与路径、其不含机密的输入/场景，
以及实际结果。对于触发，保留 Run ID；对于失败，指出
失败的块与原因。对于部署，把 URL、鉴权与启用
状态与任何执行结果分开报告。
