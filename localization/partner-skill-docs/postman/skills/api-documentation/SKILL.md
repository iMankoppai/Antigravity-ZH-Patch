# API 文档

维护良好的契约能让调用方获得足够信息，无需阅读实现即可完成集成。
把描述与示例与 API 产物放在一起，能让同一份知识同时支撑文档、测试与 mock，
且变更可与代码一同审查。

1. 从现有的权威来源开始。OpenAPI 规范描述供工具使用的
   接口；Postman 集合则增加可运行的请求、
   示例与断言。当两种用途都重要时，请同时维护两者，并明确
   生成或同步的方向，以免它们变成
   相互竞争的定义。只有当初始化或
   绑定尚未解决时，本地编辑才需要 **bootstrap**。
2. 当规范是权威来源时，使用
   `postman spec generate collection <spec-path-or-id> -n "<collection-name>"` 复用其操作。
   在替换现有集合之前，先检查生成结果：
   已维护的脚本与示例承载着端点形状之外的知识。
3. 描述会改变调用方决策的内容：必填与可选输入、
   鉴权与作用域、响应保证、分页、可重试的失败，以及
   副作用。从约定的契约或经核实的行为中推导保证；
   对于尚未解决的设计选择，请加以标注，而不是凭空编造。
   当某个设计选择影响可用性或兼容性时，使用 [REST 设计指南](reference/rest-api-best-practices.md)，
   而不是在填补文档缺口时顺便重新设计一个无关的接口。
4. 保存能阐明关键情形的示例，包括相关错误。
   示例既会成为 mock 的输入，也会成为读者的说明；
   只覆盖成功的示例会隐藏调用方必须处理的失败路径。
   本地集合编辑使用 **collection-schema-v3**，并使用 **variables**
   让凭据不进入可复用的请求与示例。
5. 根据受众选择交付方式。本地产物支持 Git 审查；
   发布到已绑定的工作区可让有访问权限的队友使用它们
   （见 **bootstrap**）。工作区 push 本身并不发布
   公开文档页面，也不更改权限。若需要公开文档链接，
   请使用 **postman-mcp-server** 的文档工作流与可用的
   发布工具；在公开暴露之前先确定目标受众。

## 验证

检查编辑后的产物能否解析，以及其示例是否与
契约一致。对于发布，请检查生成的页面并报告其实际
链接与可见性；仅一次成功的上传并不向读者展示可用的
文档。说明任何仍未记录或未经核实的行为。
