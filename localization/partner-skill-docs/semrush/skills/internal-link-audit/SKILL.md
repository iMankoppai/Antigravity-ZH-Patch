# 内部链接审计

审计一个站点的内部链接，并产出一份标注了证据来源的整改计划。回答三个问题：

1. 哪些重要页面难以或无法通过内部链接抵达？
2. 哪些内部链接是损坏的、被重定向的、不具描述性的，或以其他方式低效的？
3. 哪些上下文链接和中心页关系能让架构更清晰？

不要把内部链接当作一项配额作业。只有当来源、目的地和用户旅程在上下文中相关时，才推荐链接。

## 规则来源

在分析和最终输出中把以下证据类别区分清楚。

- **Semrush 支持的指引：** 内部链接帮助搜索引擎发现页面、传达层级与上下文、分发权重。Semrush 推荐具描述性的锚文本、相关的中心-辐射式关系，以及用上下文入站链接来支撑新内容。
- **MCP 契约要求：** 由项目支撑的发现只来自官方 Semrush MCP 返回的报告和字段。产品 UI 的特性名称不是 MCP 报告名称。
- **行业经验法则：** 基于业务重要性、可能的用户影响或整改工作量的优先级排序是分析师判断，除非有提供的第一方数据支撑。
- **用户可配置默认值：** 上限、样本和优先级权重必须适应站点的规模、目标和可用数据。绝不把它们变成普遍的 SEO 规则。

## 输入

一次性询问：

- 根域名；
- 对业务最重要的页面或页面类型；
- 任何已知的迁移、改版或架构约束；
- 用户想要一次完整的由项目支撑的审计，还是一次基于提供导出/人工的抽样。

不要要求用户粘贴 Semrush API 密钥。官方 MCP 使用 Semrush 认证。

## 官方 Semrush MCP 工作流

对每份参数尚未知晓的报告，先做发现和 schema 获取。

1. 调用 `projects`。
2. 发现 `list_projects`，获取其 schema，执行它，并精确匹配所请求的域名。确认 `siteaudit` 已激活。
3. 调用 `site_audit`。
4. 用项目 ID 发现并执行 `snapshots`。选择最新的已完成快照，并保留其 `snapshot_id` 和完成日期。
5. 执行 `info` 获取抓取状态、已抓取页面数、问题计数、重定向计数和抓取深度分布。
6. 执行 `meta_issues` 获取有效的问题 ID 和定义。这是一个目录，而不是证明每个问题都存在于该站点的证据。
7. 从 `info.defects` 读取当前的问题计数。对每个计数非零的相关问题，用项目 ID、问题 ID、快照 ID 和一个受控上限执行 `issue_details`。只在需要时分页。
8. 只有当某个确切被抓取的 URL 需要页面级检查时，才用 `page_list` 然后 `page_info`。

受测的公开 MCP 暴露的是基于问题的 Site Audit 报告，而不是字面意义上的 **Internal Linking 主题报告**。在实时契约测试中发现的相关问题 ID 包括：损坏的内部链接、孤立网站地图/Google Analytics 页面、页面抓取深度、只有一个内部链接的页面、重定向链、永久和临时重定向、nofollow 内部链接、无锚文本的链接，以及不具描述性的锚文本。始终重新发现实时目录，而不是把这些 ID 硬编码为永久契约。

Projects 访问是只读的。绝不承诺创建项目、更改抓取设置、连接 Analytics，或运行新的审计。如果没有匹配的项目或已完成的快照，说明该局限并使用回退阶梯。

## 访问与证据护栏

- 在执行前告诉用户，Semrush 查询可能消耗 API 单位。从能确立该问题的最小结果集开始，然后在用户想要详尽行时扩展。
- 空的 `issue_details` 响应意味着所选快照对该问题没有返回任何出现项。不要把它当成工具故障，也不要编造示例。
- 项目缺失、Site Audit 工具未激活、快照缺失、字段不可用或执行错误，只终止那一个数据分支。解释哪些内容无法确立。
- 不要从样本、仅凭网站地图，或人工提供的 URL 列表推断全站覆盖。
- 除非所执行的报告实际包含那些字段，否则不要声称 Site Audit 会返回自然搜索流量、转化、关键词搜索量、锚文本分布，或完整的入站链接图。

## 回退阶梯

使用可用的最强来源，并在输出中点明它。

1. 一个带有已完成 Site Audit 快照的既有 Semrush 项目。
2. 用户提供的 Semrush Site Audit 导出。
3. 爬虫导出加上网站地图，以及（如果提供）Analytics 或 Search Console 的落地页数据。
4. 网站地图加上一个以用户重要页面为中心的人工样本。
5. 用户提供的 URL 列表。

把第 3–5 级标注为抽样，除非所提供的数据能证明覆盖了整个站点。

## 工作流

### 1. 确立覆盖与架构

记录：

- 域名和所选快照的日期；
- 审计状态和已抓取页面数；
- 可用的深度分布；
- 用户提供的重要页面；
- 数据来源和覆盖局限。

只从观察到的导航、URL、网站地图或提供的文档推断架构。扁平分布本身并不证明搜索引擎无法理解该站点。

### 2. 找出孤立或链接不足的页面

孤立页面在用于识别它的数据集中没有可抓取的入站内部链接。Site Audit 可能基于网站地图或已连接的 Analytics 数据暴露单独的孤立问题；报告其来源，因为这些页面的总体是不同的。

对每个返回的 URL，确定该页面应当：

- 从上下文相关的页面或合适的中心页被链接；
- 合并或重定向到一个当前的等价页面；
- 有意排除在搜索之外；或
- 被移除，前提是经过内容、流量、转化和反向链接审查。

Semrush 的编辑指引建议在发布新内容时目标为两到三条上下文入站链接。把它当作一个编辑目标，而不是对每个既有 URL 的自动失败阈值，也不是排名改善的承诺。

除非第一方或已执行的 Semrush 数据实际确立了某页面的流量，否则不要称其为高流量孤立页面。

### 3. 审查损坏链接与重定向

对 `issue_details` 返回的每个出现项，保留来源 URL、目的地 URL（如有）、HTTP 状态或问题信息（如有）、问题 ID 和快照日期。

推荐以下之一：

- 把来源链接更新为正确的实时目的地；
- 当存在真正的替代、且更广的入站引用能证明其合理时，重定向这个过时的目的地；
- 当没有有用的目的地时移除该链接；
- 当内部链接经过可避免的重定向链时，把它们更新为最终 URL。

对永久移动使用 301 或 308，对临时移动使用 302 或 307。不要声称临时重定向本质上无法传递链接权重。

### 4. 审查抓取深度

用 `info.depths` 获取分布，用 `info.defects` 中的当前深度问题加上 `issue_details` 获取受影响 URL。Semrush Site Audit 可能标记需要超过三次点击的页面，但这是一个产品检查，不是普遍的排名法则。

当用户把某页面确定为重要，或所提供的第一方证据显示出有意义的需求或业务价值时，优先处理深度改动。不要强加关键词搜索量截断，也不要要求每个重要页面都从首页被链接。

### 5. 审查锚文本与 nofollow 问题

对缺锚文本、不具描述性锚文本和内部 nofollow 链接，在其存在当前出现项时，使用已发现的问题。

- 优先使用能自然语言描述目的地的简洁锚文本。
- 当具描述性的短语能帮助用户理解目的地时，避免像"点这里"这样的通用文字。
- 不要仅仅因为内部完全匹配锚文本是完全匹配就标记它。审查重复、上下文和可读性。
- 除非数据源提供，否则不要声称某个目的地的完整锚文本分布。
- 逐案审查内部 `nofollow`。不要笼统地说该属性会阻止一切价值流动，也不要自动命令移除它。

### 6. 推荐上下文中心页与链接

从观察到的主题关系、导航和提供的内容数据中识别中心-辐射机会。一个中心页应当为用户组织一个有意义的主题；它并不自动是内部链接最多的那个 URL。

对每条建议的链接，点明：

- 来源 URL；
- 目的地 URL；
- 该关系为何有用；
- 一个具描述性的锚文本建议；
- 证据来源；
- 置信度。

不要要求固定数量的横向链接、每个中心页都要一个首页链接，或每个聚簇都要一个新的支柱页面。

## 输出

从一份证据摘要开始：

| 证据类别     | 来源                           | 覆盖                       | 快照或日期 | 局限                   |
| ------------------ | -------------------------------- | ------------------------------ | ---------------- | ----------------------------- |
| Semrush Site Audit | 项目和快照             | 全站抓取或按配置的抓取 | 日期             | 抓取上限和集成 |
| 用户数据          | Analytics/导出/网站地图         | 陈述实际范围             | 日期             | 缺失字段或日期范围  |
| 人工观察 | 已审查的 URL                    | 抽样                         | 日期             | 非全站                  |
| 模型推断    | 架构/链接建议 | 推导                        | 日期             | 需要人工验证     |

然后提供一份按优先级排序的整改表：

| 优先级 | 问题 | 来源 URL | 目的地或受影响 URL | 证据 | 建议操作 | 置信度 |
| -------- | ----- | ---------- | --------------------------- | -------- | ------------------ | ---------- |

使用观察到的业务重要性、严重性、规模和投入来排优先级。如果用户未提供业务或表现数据，就说明这一点，并避免假装优先级等于预期的流量或收入影响。

以以下内容结尾：

1. **现在修复：** 已确认的、影响重要页面或导航的缺陷。
2. **接下来改进：** 有充分支持的上下文链接或架构机会。
3. **先验证：** 抽样、推断或依赖集成的发现。
4. **不可用的证据：** 审计无法访问的报告或字段。
