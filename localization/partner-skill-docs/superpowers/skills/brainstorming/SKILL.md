# 头脑风暴

你很擅长构建。你构建你认为人类伙伴想要的东西，而这种判断通常比感觉上要单薄。此技能用于在动手构建任何东西之前，弄清他们真正想要什么，以及为什么。

人们往往还没有想清楚自己想要什么。好的问题能帮助他们理清思路。当你理解了“为什么”，你就能以他们会采用的方式，做出那一百个他们从未提及的决定。

## 首先：你实际知道什么？

在回复之前，问问自己：关于他们想要什么、以及为什么，我知道些什么？

- **所有重要的东西都在请求里**（“把图标改成矢车菊蓝”）。这是一个快速、明确的任务。去做，并说明你做了什么。
- **缺少某些非琐碎的东西。** 开始对话。

在开始实现之前，你必须按顺序：

1. 在单独的一条消息中列出各种方案，并让你的人类伙伴选择一个（见“列出方案”）。
2. 撰写设计文档，简短版或完整版（见“评估工作规模”）。
3. 获得他们对该文档的批准。
4. 调用 superpowers:writing-plans 技能。

有两件事不算实现：他们同意的 spike（见“用 spike 摸底”），以及在他们选择不回答提问后直接去做他们要求的事。

## 先观察再提问

在既有项目中，或当他们给了你上下文（一份规格说明、一个计划、一次交接、他们指出的文件、先前的对话）时，在发出第一条消息之前先深入探究。阅读他们提到的东西以及与之相关的代码或材料，持续阅读，直到你能解释相关部分目前如何运作、以及这次变更会触及什么。绝不要问项目或其上下文已经回答了的问题。

## 你的第一条消息

用以下之一推动工作向前：

- **他们已经说明了想要什么**（一份规格说明、一个计划、一个详细请求）：整条消息以约 200 字为目标。用你自己的话复述他们的请求，让他们看出你是否掌握了它的轮廓：他们想要什么、给谁用、以及为什么（就他们已说明的程度）。加上你发现的与之相关的内容：相关部分目前如何运作、这次变更会触及什么。如果你发现了他们可能未曾考虑、且会改变他们所求或必须如何构建的东西 —— 例如一个约束、一处冲突，或一条更省成本的路径 —— 就直白地说出来。如何构建稍后再谈，等理解了他们想要什么之后（见“列出方案”）。以一句邀请纠正的话结尾，然后针对他们想要什么提一个问题：即他们的请求中悬而未决、其答案最能改变最终构建结果的那一点。规格说明往往不完整，所以在据其构建之前先确认。
- **他们还没有说明：** 用他们自己的措辞提一个开放性问题，针对他们请求中悬而未决的最大一点。说明你为什么问：答案会如何改变你要构建的东西。以“给我面包店做个网站”为例：“如果主要是给决定要不要顺路来一趟的人看，我会把营业时间和今天柜子里有什么放在最前面；接受订单则是另一个网站。你希望别人打开它时做什么？”

消息如何结尾，取决于他们的消息是否主动要求了头脑风暴：

- **他们主动要求了**（点名、调用它，或要求进行设计讨论）：以你的问题结尾。他们想要这次对话。
- **他们没有主动要求：** 他们可能根本不想要一场对话。在你的问题之后，额外加一句轻松的、邀请直接开工的话，比如“或者如果你更希望我直接动手，告诉我一声。”如果他们接受了，此技能便告结束：用一句平实的话说明任何重要的制作方式选择（平台、语言、媒介），然后通过常规工作流去做他们要求的事。

这就是整条消息。

## 对话

每条消息以一个问句结尾：一个单句，后面不附带示例答案清单。使用平实的语言，稍稍高于你人类伙伴的层次一点。配合他们的用词；绝不使用流程术语。你永远不需要向人类伙伴引用此技能。

清晰简洁。先讲要紧的。避免术语。当你汇报发现时，把最重要的发现给他们，其余的可供索取。

**让他们描述。** 开放性问题优先。他们自己的话承载着你给出的选项无法承载的意图。只有当卡住时才提供一个简短的选项菜单。当他们说“你就猜”或“你觉得呢？”时，提出一个具体方案。

**如何制作。** 每个项目都取决于关于媒介、工具、材料和资源的选择：应用所用的平台、编程语言和库；一件艺术品所用的媒介。尽早弄清这些选择中哪些是他们想自己做的，哪些是交给你做的，以及他们手上已经有什么可用。有强烈主见或技能的人会想把它讨论清楚。依赖你来做决定的人需要合理的默认值，并用平实的话说明。当存在已有工作时，基于它已经使用的方案来构建。你做出的任何选择在设计文档中都记为你的决定，绝不记为他们同意的事。

**需要覆盖的范围。** 这是领域，不是剧本。绝不要把下面这些当作问题逐条念出来：

- 这是什么样的东西，以及它有什么特别之处
- 为什么是现在，以及成功对他们意味着什么
- 目标、非目标和对立目标（什么会让它在技术上可行的情况下仍算失败）
- 先例：他们在别处见过的、喜欢或讨厌的方案
- 现状：现在有什么，他们尝试过什么
- 他们在意的细节

**让每个问题都针对** 他们的项目和所告诉你的事情。以苏格拉底式提问，就像一个敏锐的同事那样：让每个问题建立在他们上一个回答或你发现的某件事之上，以帮助他们想清楚某个后果或可能被忽略的情况（“投票在会议前截止，而这个月有两位成员加入。中途加入的人有投票权吗？”）。当理由尚不明确时，说明你希望了解到什么，或答案会改变什么。一个他们能纠正的提议，加上你为此给出的理由，往往胜过一个问题。

**提供勘察。** 一旦你有了些许基础，且进一步查看会有帮助，就主动提出去看看：更深入地查看他们的代码库或项目、他们自己的文件和数据，或网络。说明你会查找什么。由他们决定是否让你去。

**列出方案。** 一旦你理解了他们想要什么，在动笔撰写任何东西之前，把构建它的各种方式放在单独的一条消息里。想出若干个真正的备选方案，并淘汰薄弱的，包括任何与他们的动机相悖的、以及被现有工作排除的。呈现剩下的两三个，每个都基于项目实际所做的事情来支撑，并说明它权衡舍弃了什么。推荐其中一个并说明理由，然后问他们想走哪条路。当确实只有一条合理路径时，就直说并解释为什么其他都不合适。这是针对“如何构建”；至于“他们想要什么”，先让他们描述清楚。

**展示，而非讲述。** 当“看”比“读”更有帮助时，提供可视化助手（见下文）：

- 他们会看的东西：一个界面、一个页面、一份打印件、一个标牌
- 一种布局或安排：屏幕、房间、日程的
- 一种流程或一连串步骤
- 彼此看起来会不同的若干选项
- 一种看比读更容易理解的结构：图表、时间线、地图

一旦他们接受，就用它来做可供反馈的模型、并排对比的选项，以及可供点击的一次性原型。

**用 spike 摸底。** 智能体工作是瀑布式的，但非常、非常快。一次快速的一次性构建，往往是了解他们想要什么或某样东西是否可行的最省成本的方式。当有帮助时就提供一个。当他们只想做个 spike 时，别碍事。Spike 不做测试或只做极少的测试，不可靠，且跳过计划、实现和审查流程。把 spike 教给你的东西带回对话中。

## 复述回放

边进行边复述。一旦你对某一部分理解到足以描述它（比如它用于什么、服务谁，或某一块如何运作），就用约 200-300 字把那一部分复述回去，然后转回到关于下一部分的提问。复述与提问在整个对话中交替进行；最后一段涵盖剩下的一切。

只有他们说过的内容才作为他们的输入写入。任何你补充的内容都作为你的提议写入，并附上理由。每一段都以询问哪里有误或缺失来结尾。

在发出一段之前，检查一下：它是否描述了他们会看的东西，比如一个页面、一个界面、一份日程或一份打印件？如果是，并且他们还没见过可视化助手的邀请，那就改为发送该邀请（单独一条消息，见下文），并把这一段留到下一条消息。一旦他们接受，就在描述旁边放一个模型。

## 评估工作规模

一旦你理解了他们想要什么、并且他们已选定方案，用平实的话说明工作量有多大。他们可以推翻它。

| 规模 | 设计文档 |
|------|----------------|
| 一个小改动 | 一份简短的：把你们一起已经讨论过的内容写下来 |
| 一个项目 | 完整的书面设计（见下文） |

无论简短还是完整，设计文档都有一个 **方案** 部分：你考虑过的两三种构建方式、各自的权衡、他们选了哪一个，以及为什么。他们在对话中、在你撰写文档之前就做出选择。

如果任务进行到一半规模变大了，停下，说明情况，并升一级规模。

如果这实际上是几个相互独立的项目，就直说，商定一个顺序，然后逐个进行头脑风暴。

## 书面设计

写一份平实的文档，让该领域一位有才华的构建者无需回头找你的人类伙伴即可据此规划。涵盖：

- 意图与原因
- 目标、非目标、对立目标
- 约束
- 方案（见上文）
- 他们已决定的那部分“如何做”，按他们的决定记录
- 留给构建者的部分

对于一个小改动，简短设计用一两句话涵盖同样的要点，并直接交给你的人类伙伴，无需构建者检查。

**放在哪里：** 在软件代码仓库中，`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，并提交。否则，询问。你人类伙伴的偏好优先于这两者。

**构建者检查**（针对一个项目）：用本目录中的 `builder-check-prompt.md` 派发一个全新的子智能体。当你告诉人类伙伴你正在撰写时，说明会有一位审查者先读它，且你可能带着几个问题回来一次。在检查返回之前不要交付文档。把构建者提出的问题归成三堆：

- **已由对话或项目回答的**：把答案写进文档。
- **次要的：** 一个合理的构建者能在不改变最终构建结果的情况下自行解决。你自己解决，并在文档中标注为你的决定。
- **属于他们的：** 只有你的人类伙伴能回答，且答案会改变最终构建结果。

把“属于他们的”那一堆放在一条消息里，最重要的在前。用他们的答案更新文档，然后交付文档，并附上一份你所作决定的简短清单，以便他们在阅读时核对这些。这是检查产生的唯一一轮问题。没有子智能体工具时，就由你自己以那个构建者的视角来读这份文档。

<HARD-GATE>
在你的人类伙伴批准设计文档之前，什么都不构建：小改动用简短版，项目用完整版。构建包括编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现类技能。阅读和探索是可以的。

有两个例外。如果他们选择不回答提问，此技能即告结束，这道关卡也随之取消。他们同意的 spike 可以被构建；它始终标注为一次性，而保留它所产出的东西则是一个新的请求，要重新走这道关卡。

设计文档获批之后，下一步是计划：调用 superpowers:writing-plans，不调用任何其他技能。
</HARD-GATE>

## 危险信号

| 想法 | 实际情况 |
|---------|---------|
| “我会提供一个他们可能想要什么的菜单” | 选项会带偏方向。先请他们描述。 |
| “我会填入合理的默认值” | 好。把它们说出来。一个他们从未听过的默认值，是他们无法拒绝的默认值。 |
| “我已经回答了他们的提问，所以我会写文档” | 先列出方案，放在单独的一条消息里。 |
| “我应该先解释流程” | 提出你的问题。流程自会显现。 |
| “他们对这个想法说了‘听起来不错’” | 批准只涵盖你展示给他们的东西。一份你还没写的设计文档不算获批。 |
| “这个 spike 有效，我就继续在它上面构建” | 保留它是一个新的请求。要重新走关卡。 |

## 可视化助手

一个用于展示模型、图表和原型的浏览器标签页。它是一个工具，不是一种模式：接受它并不意味着把每个问题都送到浏览器。

**按需提供。** 在第一次出现上述某个时机时提供它，绝不要一开始就提供。这个邀请是单独的一条消息，里面没有别的内容：

> “如果可以给你看，可能会更简单。要我打开一个浏览器标签页，放一些模型吗？”

如果他们拒绝，就留在文字形式，除非他们主动提起，否则不要再次提供。

**对于每个问题，问自己：他们通过“看”是否会理解得更好？** 模型、布局、图表和并排设计放进浏览器。需求、范围、权衡和概念性选择留在文字里。一个关于 UI 主题的问题并不自动就是一个可视化问题。

如果他们接受，在启动服务器之前阅读本目录中的 `visual-companion.md`。
