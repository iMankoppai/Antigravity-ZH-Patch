# 编写技能

## 概述

**编写技能就是把测试驱动开发应用于流程文档。**

**个人技能放在你运行时的技能目录里**（Claude Code 上是 `~/.claude/skills/`）——各个运行时上的路径见 [codex-tools.md](../using-superpowers/references/codex-tools.md) 或 [gemini-tools.md](../using-superpowers/references/gemini-tools.md)。Codex、Copilot CLI 和 Gemini CLI 也都认可 `~/.agents/skills/` 作为一个跨运行时别名。

你编写测试用例（带子智能体的压力场景），看着它们失败（基线行为），编写技能（文档），看着测试通过（智能体遵从），然后重构（堵住漏洞）。

**核心原则：** 如果你没有亲眼看着一个智能体在没有该技能时失败，你就不知道这个技能教的是不是正确的东西。

**必需的背景：** 在使用本技能之前，你必须理解 superpowers:test-driven-development。那个技能定义了根本的 RED-GREEN-REFACTOR 循环。本技能把 TDD 适配到文档上。

**官方指引：** 关于 Anthropic 官方的技能编写最佳实践，见 references/anthropic-best-practices.md。该文档提供了额外的模式与指引，补足本技能中以 TDD 为核心的方法。

## 什么是技能？

一个**技能**是经过验证的技术、模式或工具的参考指南。技能帮助未来的智能体找到并运用有效的方法。

**技能是：** 可复用的技术、模式、工具、参考指南

**技能不是：** 关于你某一次如何解决问题的叙述

## 技能的 TDD 映射

| TDD 概念 | 技能创建 |
|-------------|----------------|
| **测试用例** | 带子智能体的压力场景 |
| **生产代码** | 技能文档（SKILL.md） |
| **测试失败（RED）** | 智能体在没有技能时违反规则（基线） |
| **测试通过（GREEN）** | 智能体在技能存在时遵从 |
| **重构** | 在保持遵从的同时堵住漏洞 |
| **先写测试** | 在编写技能之前运行基线场景 |
| **看着它失败** | 记录智能体使用的确切合理化说辞 |
| **最少的代码** | 编写针对那些具体违反行为的技能 |
| **看着它通过** | 核实智能体现在遵从 |
| **重构循环** | 发现新的合理化说辞 → 堵住 → 重新核实 |

整个技能创建过程都遵循 RED-GREEN-REFACTOR。

## 何时创建一个技能

**在以下情况创建：**
- 某项技术对你来说并非直观显然
- 你会跨项目再次引用它
- 模式适用范围广（不是项目专属）
- 其他人会受益

**不要为以下情况创建：**
- 一次性解决方案
- 别处已有良好文档的标准做法
- 项目专属约定（放进你的指令文件）
- 机械性约束（如果可以用正则/校验强制执行，就自动化它——把文档留给需要判断的场合）

## 技能类型

### 技术
带步骤的具体方法（condition-based-waiting、root-cause-tracing）

### 模式
思考问题的方式（flatten-with-flags、test-invariants）

### 参考
API 文档、语法指南、工具文档（office 文档）

## 目录结构


```
skills/
  skill-name/
    SKILL.md              # Main reference (required)
    supporting-file.*     # Only if needed
```

**扁平命名空间** —— 所有技能都在一个可搜索的命名空间里

**单独文件的用途：**
1. **重型参考**（100+ 行）—— API 文档、完整的语法
2. **可复用的工具** —— 脚本、实用程序、模板

**保持内联：**
- 原则与概念
- 代码模式（< 50 行）
- 其他一切

## 编写 SKILL.md

一个技能的 `description` 只说明何时使用它：触发条件和症状，以"当……时使用"开头。它绝不要概括技能的工作流，因为一个读到工作流摘要的智能体会转而遵循摘要，而不是去读技能。

当你编写或更改一个技能的 frontmatter、名称或 description，或需要缩减它的体量时，阅读 [references/discovery.md](references/discovery.md)：其中的 SKILL.md 模板、description 与关键词指引、命名、token 预算，以及与其他技能的交叉引用。

## 流程图

当你添加或更改技能中的流程图时，先阅读 [references/flowcharts.md](references/flowcharts.md)：何时一个流程图值得保留、graphviz 的约定，以及如何渲染它。

## 代码示例

**一个出色的示例胜过多段平庸的示例**

选择最相关的语言：
- 测试技术 → TypeScript/JavaScript
- 系统调试 → Shell/Python
- 数据处理 → Python

**好的示例：**
- 完整且可运行
- 注释充分，解释为什么
- 来自真实场景
- 清晰地展示模式
- 可直接改造（不是通用模板）

**不要：**
- 用 5 种以上语言实现
- 创建填空式模板
- 编写牵强的示例

你擅长移植——一个出色的示例就够了。

## 文件组织

### 自成一体的技能
```
defense-in-depth/
  SKILL.md    # Everything inline
```
何时：所有内容都装得下，不需要重型参考

### 带可复用工具的技能
```
condition-based-waiting/
  SKILL.md    # Overview + patterns
  example.ts  # Working helpers to adapt
```
何时：工具是可复用的代码，而不只是叙述

### 带重型参考的技能
```
pptx/
  SKILL.md       # Overview + workflows
  pptxgenjs.md   # 600 lines API reference
  ooxml.md       # 500 lines XML structure
  scripts/       # Executable tools
```
何时：参考资料大到无法内联

通过它们的解释器在正文中调用随附脚本（`bash scripts/tool.sh`、`node scripts/tool.js`），绝不要用裸路径：有些 harness 插件打包器会剥掉可执行位，在那里裸的 `scripts/tool.sh` 会以 `Permission denied` 失败。

## 铁律（与 TDD 相同）

```
没有失败的测试，就不写技能
```

这既适用于新技能，也适用于对既有技能的编辑。

在测试之前写技能？删掉它。重新开始。
不经测试就编辑技能？同样的违反。

**没有例外：**
- 不为"简单的补充"
- 不为"只是加一节"
- 不为"文档更新"
- 不要把未经测试的改动留作"参考"
- 不要在运行测试时"改造"
- 删掉就是删掉

**必需的背景：** superpowers:test-driven-development 技能解释了为什么这很重要。同样的原则适用于文档。

## 测试所有技能类型

不同的技能类型需要不同的测试方法：

### 纪律强制型技能（规则/要求）

**示例：** TDD、verification-before-completion、designing-before-coding

**用以下方式测试：**
- 学术性问题：他们理解规则吗？
- 压力场景：他们在压力下会遵从吗？
- 多种压力叠加：时间 + 沉没成本 + 疲惫
- 识别合理化说辞并添加明确的回击

**成功标准：** 智能体在最大压力下遵守规则

### 技术型技能（操作指南）

**示例：** condition-based-waiting、root-cause-tracing、defensive-programming

**用以下方式测试：**
- 应用场景：他们能正确地运用该技术吗？
- 变体场景：他们能处理边界情况吗？
- 缺失信息测试：指令有缺漏吗？

**成功标准：** 智能体成功地把技术运用到新场景

### 模式型技能（心智模型）

**示例：** reducing-complexity、information-hiding 概念

**用以下方式测试：**
- 识别场景：他们能识别出模式何时适用吗？
- 应用场景：他们能使用这个心智模型吗？
- 反例：他们知道何时不该应用吗？

**成功标准：** 智能体正确地识别何时/如何应用模式

### 参考型技能（文档/API）

**示例：** API 文档、命令参考、库指南

**用以下方式测试：**
- 检索场景：他们能找到正确的信息吗？
- 应用场景：他们能正确地使用所找到的东西吗？
- 缺漏测试：常见用例都覆盖了吗？

**成功标准：** 智能体找到并正确地应用参考信息

## 跳过测试的常见合理化

| 借口 | 现实 |
|--------|---------|
| "技能显然很清晰" | 对你清晰 ≠ 对其他智能体清晰。测一测。 |
| "它只是一个参考" | 参考也可能有缺漏、含糊的章节。测试检索。 |
| "测试是杀鸡用牛刀" | 未经测试的技能有问题。总是如此。15 分钟的测试省下数小时。 |
| "有问题冒出来我再测" | 问题 = 智能体没法用这个技能。在部署之前测试。 |
| "测起来太繁琐" | 测试比在生产里调试糟糕的技能更省事。 |
| "我确信它很好" | 过度自信保证出问题。照样测。 |
| "学术性审阅就够了" | 读 ≠ 用。测试应用场景。 |
| "没时间测试" | 部署未经测试的技能会在以后浪费更多时间去修。 |

**所有这些都意味着：部署之前测试。没有例外。**

## 让形式匹配失败

在编写指引之前，先给基线失败分类。让一种失败类型变得滴水不漏的形式，会在另一种失败类型上可衡量地适得其反。

| 基线失败 | 正确的形式 | 错误的形式 |
|---|---|---|
| 在压力下跳过/违反规则（明知更好，仍然去做） | 禁止 + 合理化表 + 危险信号（见 references/bulletproofing.md） | 软性指引（"优先……"、"考虑……"） |
| 遵从了，但输出形状不对（提示词臃肿、结论被埋、复述规格） | 正向配方或契约：说明输出就是什么——它的各部分，按顺序 | 禁止清单（"不要复述"、"绝不叙述"） |
| 从他们已经产出的东西里遗漏了某个必需元素 | 结构化：在他们填写的模板里设置必需字段或槽位 | 模板附近的散文式提醒 |
| 行为应当取决于某个条件 | 以可观察谓词为键的条件式（"如果 brief 存在，就引用它"） | 无条件的规则 + 豁免条款 |

**为什么禁止在塑造类问题上适得其反：** 在一个竞争性激励之下（"让提示词自包含"），智能体会跟"不要 X"讨价还价。在关于派发提示词指引的正面对比措辞测试中，禁止分支产生的多余内容明显多于配方分支（分布完全分离），而且趋势上甚至比无指引的对照组还差——对你自己的情形做微型测试，而不是想当然，但绝不要默认去用禁止。配方不留下任何讨价还价的余地：输出要么匹配所声明的形状，要么不匹配。

**无论你选哪种形式，都要遵守的规则：**
- **不要细节条款。** "除非重要，否则不要 X"会重新打开讨价还价——在同样的措辞测试中，给一个胜出的配方附加一条细节条款，就把它从一致降级为嘈杂。把真正的例外表达为它自己的、以可观察谓词为键的条件式。
- **豁免条款并不划定范围。** "这个限制不适用于代码块"仍然会压制代码块。如果输出的一部分必须豁免，就重构结构，使规则无法触及它。

## 防合理化滴水不漏

当基线失败是纪律失败时，在你编写指引之前先阅读 [references/bulletproofing.md](references/bulletproofing.md)：堵住漏洞、精神与字面的界线、合理化表，以及危险信号清单。

## 技能的 RED-GREEN-REFACTOR

遵循 TDD 循环：

### RED：编写失败的测试（基线）

在**没有**技能的情况下带子智能体运行压力场景。记录确切的行为：
- 他们做出了什么选择？
- 他们使用了什么合理化说辞（逐字记录）？
- 哪些压力触发了违反？

这就是"看着测试失败"——你必须在编写技能之前看清智能体自然状态下会做什么。

### GREEN：编写最少的技能

编写针对那些具体合理化说辞的技能。不要为假设的情况添加额外内容。

在**有**技能的情况下运行同样的场景。智能体现在应当遵从。

### REFACTOR：堵住漏洞

智能体发现了新的合理化说辞？添加明确的回击。重新测试，直到滴水不漏。

### 在完整场景之前做措辞微型测试

完整的压力场景运行是最终的关卡，但每次迭代都慢且昂贵。先用微型测试核实措辞本身：

1. **每次调用一个全新上下文的样本**——一次裸 API 调用，或如果你没有 API 访问权限，则用单发子智能体。系统提示词 = 该指引将要栖身的真实上下文（完整的技能或提示词模板，而不是孤立的该指引）；用户消息 = 一个诱发该失败的任务。
2. **始终包含一个无指引的对照。** 如果对照没有表现出这种失败，那就没有什么要修的——停下，不要编写这条指引。
3. **每个变体 5+ 次重复。** 单次样本会撒谎。
4. **手动阅读每一个被标记的匹配。** 如果你喜欢，可以程序化打分，但模板回显和引用的反例会伪装成命中；仅凭自动化计数会同时高估失败和成功。
5. **方差是一个指标。** 当指引奏效时，各次重复会收敛到相同的形状。五次重复出现五种不同的解释，意味着措辞没有约束力——在增加文字之前先收紧形式。

微型测试核实措辞；它们不能替代纪律型技能的压力场景。

**测试方法论：** 完整的测试方法论见 [references/testing-skills-with-subagents.md](references/testing-skills-with-subagents.md)：
- 如何编写压力场景
- 压力类型（时间、沉没成本、权威、疲惫）
- 系统地堵住漏洞
- 元测试技术

## 反模式

### ❌ 叙述性示例
"在 2025-10-03 的会话中，我们发现空的 projectDir 会导致……"
**为什么不好：** 太具体，不可复用

### ❌ 多语言稀释
example-js.js、example-py.py、example-go.go
**为什么不好：** 质量平庸，维护负担

### ❌ 流程图里的代码
```dot
step1 [label="import fs"];
step2 [label="read file"];
```
**为什么不好：** 无法复制粘贴，难以阅读

### ❌ 通用标签
helper1、helper2、step3、pattern4
**为什么不好：** 标签应当具有语义含义

## 停下：在转向下一个技能之前

**在编写任何技能之后，你必须停下并完成部署流程。**

**不要：**
- 不逐个测试就批量创建多个技能
- 在当前技能被验证之前转向下一个技能
- 因为"批量更高效"而跳过测试

**下面的部署清单对每一个技能都是强制性的。**

部署未经测试的技能 = 部署未经测试的代码。这违反质量标准。

## 技能创建清单（TDD 适配版）

**重要：为下面的每一个清单项创建一个 todo。**

**RED 阶段 - 编写失败的测试：**
- [ ] 创建压力场景（纪律型技能需要 3+ 种叠加压力）
- [ ] 在没有技能的情况下运行场景 - 逐字记录基线行为
- [ ] 识别合理化说辞/失败中的模式

**GREEN 阶段 - 编写最少的技能：**
- [ ] 名称只使用字母、数字、连字符（不含括号/特殊字符）
- [ ] YAML frontmatter 带有必需的 `name` and `description` 字段（最多 1024 字符；见 [spec](https://agentskills.io/specification)）
- [ ] Description 以"Use when..."开头，并包含具体的触发器/症状
- [ ] Description 以第三人称书写
- [ ] 贯穿全文放置用于搜索的关键词（错误、症状、工具）
- [ ] 带有核心原则的清晰概述
- [ ] 针对 RED 阶段识别出的具体基线失败
- [ ] 指引形式匹配失败类型（见 让形式匹配失败）
- [ ] 对于塑造行为的指引：措辞已对照无指引对照做微型测试（5+ 次重复，每个被标记的匹配都手动阅读）——纯参考型技能不适用
- [ ] 代码内联，或链接到单独文件
- [ ] 一个出色的示例（不是多语言）
- [ ] 在有技能的情况下运行场景 - 核实智能体现在遵从

**REFACTOR 阶段 - 堵住漏洞：**
- [ ] 从测试中识别出新的合理化说辞
- [ ] 添加明确的回击（如果是纪律型技能）
- [ ] 从所有测试迭代中构建合理化表
- [ ] 创建危险信号清单
- [ ] 重新测试，直到滴水不漏

**质量检查：**
- [ ] 仅在决策不明显时才放入小型流程图
- [ ] 快速参考表
- [ ] 常见错误一节
- [ ] 没有叙述性讲故事
- [ ] 支持文件仅用于工具或重型参考

**部署：**
- [ ] 把技能提交到 git 并推送到你的 fork（如果已配置）
- [ ] 考虑通过 PR 回馈（如果广泛有用）

## 发现工作流

未来的智能体如何找到你的技能：

1. **遇到问题**（"测试不稳定"）
2. **搜索技能**（grep 描述、浏览分类）
3. **找到 SKILL**（描述匹配）
4. **浏览概述**（这相关吗？）
5. **阅读模式**（快速参考表）
6. **加载示例**（仅在实现时）

**针对这个流程优化**——把可搜索的术语早早、频繁地放置。
