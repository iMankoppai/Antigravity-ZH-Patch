# 系统化调试

## 概述

**核心原则：** 永远先找到根本原因，再尝试修复。粉饰症状即为失败。

**违反本流程的字面要求，就是违反调试的精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果你还没完成第 1 阶段，你就不能提出修复。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用：**
- 在时间压力下（紧急情况会让猜测变得诱人）
- “就一个快速修复”看起来显而易见
- 你已经尝试过多个修复
- 之前的修复没起作用
- 你还没完全理解问题

**在以下情况不要跳过：**
- 问题似乎很简单（简单的 bug 也有根本原因）
- 你很急（赶工必然导致返工）
- 经理要求现在就修好（系统化比乱撞更快）

## 四个阶段

你必须完成每个阶段才能进入下一个阶段。

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 它每次都发生吗？
   - 如无法复现 → 收集更多数据，不要猜

3. **检查最近的改动**
   - 改了什么可能导致这个？
   - Git diff、最近的提交
   - 新依赖、配置改动
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复之前，添加诊断埋点：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示出：** 哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误位于调用栈深处时：**

   参见本目录中的 `root-cause-tracing.md` 以了解完整的反向追踪技术。

   **简要版：**
   - 错误的值源自何处？
   - 是谁用错误的值调用了这里？
   - 一直向上追踪，直到找到源头
   - 在源头修复，而不是在症状处

### 阶段 2：模式分析

**在修复之前先找到模式：**

1. **寻找可用的示例**
   - 在同一代码库中定位类似的可运行代码
   - 有什么可用的东西与坏掉的东西类似？

2. **对照参考资料**
   - 如果实现某种模式，完整地阅读参考实现
   - 不要略读 —— 读每一行
   - 在应用之前完全理解该模式

3. **识别差异**
   - 可用的和坏掉的之间有何不同？
   - 列出每一处差异，无论多小
   - 不要假设“那不可能是原因”

4. **理解依赖**
   - 它需要哪些其他组件？
   - 需要什么设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 明确陈述：“我认为 X 是根本原因，因为 Y”
   - 把它写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做最小的可能改动来检验假设
   - 一次一个变量
   - 不要一次修复多个东西

3. **继续之前先核实**
   - 起作用了吗？是 → 阶段 4
   - 没起作用？形成新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说“我不理解 X”
   - 不要假装知道
   - 寻求帮助
   - 进一步研究

### 阶段 4：实现

**修复根本原因，而不是症状：**

1. **创建失败的测试用例**
   - 最简单的复现
   - 尽可能自动化测试
   - 没有框架时用一次性测试脚本
   - 修复前必须有
   - 使用 `superpowers:test-driven-development` 技能来编写正确的失败测试

2. **实现单一修复**
   - 针对已识别的根本原因
   - 一次一个改动
   - 不做“顺便”改进
   - 不捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有弄坏其他测试吗？
   - 问题真的解决了吗？
   - 在声称成功之前使用 `superpowers:verification-before-completion` 技能

4. **如果修复不起作用**
   - 停下
   - 数一数：你已经尝试了多少个修复？
   - 如果 < 3：回到阶段 1，用新信息重新分析
   - **如果 ≥ 3：停下并质疑架构（见下文第 5 步）**
   - 没有架构讨论就不要尝试第 4 个修复

5. **如果 3 个以上修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每个修复都在不同地方揭示新的共享状态/耦合/问题
   - 修复需要“大规模重构”才能实现
   - 每个修复都在别处造出新症状

   **停下并质疑根本前提：**
   - 这个模式从根本上站得住脚吗？
   - 我们是不是“仅凭惯性而坚持它”？
   - 我们应该重构架构，还是继续修症状？

   **在尝试更多修复之前，与你的人类伙伴讨论**

   这不是一个失败的假设 —— 这是一个错误的架构。

## 危险信号 —— 停下并遵循流程

如果你发现自己这样想：
- “先快速修一下，回头再调查”
- “就试着改一下 X，看看行不行”
- “加上多个改动，跑测试”
- “跳过测试，我手动验证”
- “大概是 X，我来修它”
- “我没完全理解，但这可能管用”
- “模式说是 X，但我会换个方式改”
- “主要问题如下：[不经调查就列出修复]”
- 在追踪数据流之前就提出解决方案
- **“再试一个修复”（当已经试过 2 个以上）**
- **每个修复都在不同地方揭示新问题**

**所有这些都意味着：停下。回到阶段 1。**

**如果 3 个以上修复失败：** 质疑架构（见阶段 4.5）

## 你的人类伙伴暗示你做错了的信号

**留意这些纠正：**
- “那不是没发生吗？” - 你没核实就假设了
- “它会告诉我们……吗？” - 你本应加入证据收集
- “别猜了” - 你没理解就提出修复
- “好好深入想想” - 质疑根本前提，而不只是症状
- “我们卡住了？”（沮丧） - 你的方法不管用

**当你看到这些时：** 停下。回到阶段 1。

## 常见借口

| 借口 | 实际情况 |
|--------|---------|
| “问题很简单，不需要流程” | 简单问题也有根本原因。对简单 bug，流程很快。 |
| “紧急情况，没时间走流程” | 系统化调试比猜来猜去地乱撞更快。 |
| “先试这个，然后再调查” | 第一个修复会定下模式。从一开始就做对。 |
| “我会在确认修复有效后再写测试” | 未经测试的修复不牢靠。先测试才能证明它。 |
| “一次多个修复省时间” | 无法隔离出是什么起了作用。会引出新 bug。 |
| “参考太长，我改一下模式就行” | 部分理解必然导致 bug。完整读它。 |
| “我看到问题了，让我修它” | 看到症状 ≠ 理解根本原因。 |
| “再试一个修复”（在 2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，别再修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 阅读错误、复现、检查改动、收集证据 | 理解“是什么”和“为什么” |
| **2. 模式** | 寻找可用示例、比较 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 假设得到确认或形成新假设 |
| **4. 实现** | 创建测试、修复、验证 | bug 解决、测试通过 |

## 当流程揭示“没有根本原因”

如果系统化调查揭示问题确实属于环境、时序相关或外部因素：

1. 你已完成流程
2. 记录你所调查的内容
3. 实现适当的处理（重试、超时、错误消息）
4. 添加监控/日志以供未来调查

**但是：** 95% 的“没有根本原因”情况都是不完整的调查。
