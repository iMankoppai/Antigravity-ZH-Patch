# 完成前验证

## 概述

**核心原则：** 永远先证据，后断言。

**违反这条规则的字面就是违反这条规则的精神。**

## 铁律

```
没有新鲜的验证证据，就不作完成声明
```

如果你没有在本条消息里运行验证命令，你就不能声称它通过。

## 门控函数

```
在声称任何状态或表达满意之前：

1. 确认：什么命令能证明这个声明？
2. 运行：执行完整的命令（新鲜的、完整的）
3. 阅读：完整输出，检查退出码，统计失败数
4. 核实：输出是否印证了该声明？
   - 如果否：用证据陈述实际状态
   - 如果是：用证据陈述该声明
5. 只有到这时：才做出声明

跳过任何一步 = 撒谎，而非验证
```

## 常见的失败

| 声明 | 需要 | 不充分 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 个失败 | 上一次运行、"应该会通过" |
| Linter 干净 | Linter 输出：0 个错误 | 部分检查、外推 |
| 构建成功 | 构建命令：退出码 0 | Linter 通过、日志看起来不错 |
| 缺陷已修复 | 测试原始症状：通过 | 改了代码、假定已修复 |
| 回归测试有效 | 已验证红-绿循环 | 测试通过一次 |
| 智能体已完成 | VCS diff 显示改动 | 智能体报告"成功" |
| 需求已满足 | 逐行清单 | 测试通过 |

## 危险信号 - 停下

- 使用"应该"、"大概"、"似乎"
- 在验证之前表达满意（"太好了！"、"完美！"、"完成了！"等）
- 即将未经验证就提交/推送/创建 PR
- 相信智能体的成功报告
- 依赖部分验证
- 想着"就这一次"
- 疲惫且想让工作结束
- **任何暗示成功、却未运行验证的措辞**

## 防合理化

| 借口 | 现实 |
|--------|---------|
| "现在应该能运行了" | 运行验证 |
| "我很有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "智能体说成功了" | 独立核实 |
| "我累了" | 疲惫 ≠ 借口 |
| "部分检查就够了" | 部分什么都证明不了 |
| "换了个说法，所以规则不适用" | 精神重于字面 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] "所有测试通过"
❌ "现在应该能通过了" / "看起来正确"
```

**回归测试（TDD 红-绿）：**
```
✅ 写 → 运行（通过）→ 回退修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ "我写了一个回归测试"（没有红-绿验证）
```

**构建：**
```
✅ [运行构建] [看到：退出码 0] "构建通过"
❌ "Linter 通过了"（Linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 建立清单 → 逐项核实 → 报告缺漏或完成
❌ "测试通过了，阶段完成"
```

**智能体委派：**
```
✅ 智能体报告成功 → 检查 VCS diff → 核实改动 → 报告实际状态
❌ 相信智能体报告
```

## 何时适用

**始终在以下之前：**
- 任何形式/变体的成功或完成声明
- 任何表达满意
- 任何关于工作状态的正面陈述
- 提交、创建 PR、完成任务
- 转向下一个任务
- 委派给智能体

**规则适用于：**
- 确切的短语
- 释义和同义词
- 对成功的暗示
- 任何暗示完成/正确的沟通
