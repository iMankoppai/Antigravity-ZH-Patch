# 应用设计系统

使用已连接的 Spacefast 工具。在代码仓库中工作时，保留无关的文件和改动。

如果任务需要某个现有 Space 且其身份不明确，调用 `choose_space`。将选中的 Space 作为目标。选中并不代表批准发布或其他改动。

在执行管理操作前，阅读 [references.md](references.md) 中的 MCP 调用、审批与工作模式规则。

1. 确定团队以及目标项目或 Space。对于已链接的代码仓库，读取 `.spacefast/space.json`；对于没有完整源码的现有 Space，遵循 references.md 中的源码编辑（Source edits）。不要把已提供的文件当作源码。
2. 阅读 references.md 中的团队记忆与技能（Team Memories and Skills）以及设计系统（Design system）。获取当前上下文、适用的记忆、已启用的团队技能和资源。从已保存的记录中还原被截断的指引或不可用的资源；不要凭空编造缺失的标准。
3. 在发布或部署新建或变更的源码之前，针对当前已保存的标准以及将要部署的确切源码/构建，运行 verify-design-system 技能。在桌面端和移动端宽度下检查受影响的页面和状态，并报告差距。仅在源码/构建和设计修订未变时复用验证结果。将缺失的标准报告为不可用，而非通过。启用 autoDeploy 时，在向源码工作区提交前先验证。遵循用户已有的发布意图和审批规则。
4. 当项目需要长期交接时，刷新 `design.md` 中自动生成的部分，同时保留用户撰写的内容。编辑前将适用规则映射到实际的组件、样式、文案、模式和状态。
5. 下载并检查所需的品牌文件。将面向访客的副本放入项目常规的资源源码目录；切勿嵌入私有的 Media Library URL，也不要拼凑近似一个缺失的 logo。
6. 在完整源码中执行所需的构建或编辑。运行真实构建，检查有代表性的桌面端与移动端渲染结果及相关状态，修复可处理的偏差，并重复受影响的检查。
7. 报告设计修订、变更的源码、视觉证据和剩余差距。仅依据原始请求和当前工作模式进行发布。
