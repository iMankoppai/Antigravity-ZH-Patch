# 更新现有设计

使用已连接的 Spacefast 工具。在代码仓库中工作时，保留无关的文件和改动。

如果任务需要某个现有 Space 且其身份不明确，调用 `choose_space`。将选中的 Space 作为目标。选中并不代表批准发布或其他改动。

在执行管理操作前，阅读 [references.md](references.md) 中的 MCP 调用、审批与工作模式规则。

1. 仅确定指定的现有 Space 或已链接项目、其确切的可编辑源码修订版本，以及其当前的预览或线上版本。阅读 references.md 中的设计系统（Design system）和源码编辑（Source edits），包括工作模式。
2. 阅读 references.md 中的团队记忆与技能（Team Memories and Skills）。获取当前标准、适用的记忆、已启用的团队技能和资源。在可靠时与上一次应用的交接进行对比；否则检查相关实现，不要假定每一处差异都可以安全替换。
3. 将受影响的规则映射到实际的组件、文案、状态和资源文件。保留无关的内容、行为、用户撰写的交接文本以及独立的设计选择。
4. 更新源码和资源副本，运行真实构建，并针对当前标准检查桌面端、移动端和受影响的状态。修正偏差并重复检查。
5. 在发布或部署新建或变更的源码之前，针对当前已保存的标准以及将要部署的确切源码/构建，运行 verify-design-system 技能。在桌面端和移动端宽度下检查受影响的页面和状态，并报告差距。仅在源码/构建和设计修订未变时复用验证结果。将缺失的标准报告为不可用，而非通过。启用 autoDeploy 时，在向源码工作区提交前先验证。遵循用户已有的发布意图和审批规则。
6. 依据原始请求和工作模式保存并部署，在开始另一次构建前检查 autoDeploy。在请求的部署后验证线上路由；分别报告源码、预览和线上状态。
7. 对于多个指定的 Space，保持各自独立的基线、验证和回执。不要在未提及的 Space 之间滚动推行变更。
