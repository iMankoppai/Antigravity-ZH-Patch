# Looker 性能优化器

本主开发者技能管辖在新建或现有 Looker 项目中审计、诊断和优化查询性能的生命周期。它强制实施严格的性能优先设计、数据库缓存对齐、策略性数据物化，以及使用并行子智能体和 Looker MCP 工具的高级 SQL 剖析。

在本技能下开发的所有优化都必须与方言无关、对数据库高效，并保持现有业务逻辑的完整性。

---

## 1. 运行模式（预防型与响应型）

本技能在两种不同模式下运行，以在开发生命周期的不同阶段处理性能问题：

### 模式 A：按设计实现性能（预防型工程）
在向现有项目添加*新*的探索、视图或持久派生表（PDT）时使用此模式。智能体**必须**确保性能从第一秒起就经过设计：
1.  **正确的连接基数**：立即声明精确的连接关系（`many_to_one`、`one_to_one`），以防止编译器驱动的对称聚合。
2.  **PDT 索引与分区**：每个新的 PDT 定义**必须**根据最常用作仪表板筛选器的字段声明分区键和聚类/索引键。
3.  **与 ETL 对齐的缓存**：每个新探索**必须**分配到一个由 ETL/ELT 元数据查询触发的集中式 `datagroup`，避免任意设定的 `persist_for` 时间窗。

### 模式 B：主动性能调优（响应型存量优化）
在诊断和优化生产中运行缓慢的仪表板或探索时使用此模式。智能体**必须**执行此 5 阶段性能流水线：
1.  **美学审计与基线**：切换到开发者模式，并通过 Looker MCP 或 CLI 对缓慢的仪表板图块运行基线测试。记录查询运行时间、查询 ID 和数据库成本（扫描字节数/使用的 slot 数）。
2.  **并行查询剖析（子智能体辅助）**：生成专门化的子智能体来并发分析生成的 SQL 和运行 `EXPLAIN` 计划，隔离数据库瓶颈（委托规则见第 6 节）。
3.  **精准性能重构**：对 LookML 层应用有针对性的局部化编辑：
    *   对齐缓存 datagroup。
    *   将繁重的转换物化为 PDT（遵循 PDT 决策矩阵）。
    *   修正连接关系并实施连接剪枝。
4.  **验证与增量测量**：重新运行编译器（`health_analyze`）以确保零语法错误，重新执行查询，并记录性能提升矩阵。
5.  **安全的生产部署**：将优化并验证过的 LookML 分支部署到生产环境。

## 2. 缓存与 ETL 对齐规则

调优缓存是降低数据仓库成本和加速仪表板加载最快的方式。

*   **禁止任意持久化时间**：在生产环境中，严格**禁止**在探索上使用普通的 `persist_for: "24 hours"` 或类似的静态时长。这会导致数据陈旧以及冗余且昂贵的数据库查询。
*   **强制使用 Datagroup**：所有探索**必须**从模型文件中定义的集中式 `datagroup` 继承其缓存策略。
*   **ETL 触发的缓存**：Datagroup **必须**由监控仓库实际数据刷新频率的 `sql_trigger_value` 查询触发（例如查询 ETL 元数据表或检查 `MAX(created_at)`）。
*   **防止缓存失效的保障措施**：定义一个合理的 `max_cache_age`（例如 24 小时）作为回退，这样如果 ETL 流水线未能更新，缓存最终会过期，确保用户不会看到极度陈旧的数据。

## 3. 持久派生表（PDT）物化规则

当复杂连接和行级转换的即时 SQL 编译耗时过长时，必须将数据物化为持久派生表（PDT）。

### A. 主 PDT 决策矩阵
在将视图或探索转换为 PDT 之前，智能体**必须**使用此 4 象限决策矩阵评估查询：

| 指标 / 象限 | 物化为 PDT | 保持为实时查询 |
| :--- | :--- | :--- |
| **1. 复杂度** | 查询执行繁重的转换（例如复杂的正则、字符串解析、窗口函数）或多层连接，执行时间**超过 10 秒**。 | 查询执行简单的筛选和干净、带索引的连接，执行时间**低于 3 秒**。 |
| **2. 频率** | 该探索/仪表板很关键、并发很高，每天被业务用户打开数百次。 | 该探索仅被高级数据分析师偶尔用于临时深入分析。 |
| **3. 数据新鲜度** | 业务需要每小时、每天或近实时更新，符合标准重建计划。 | 业务需要绝对的秒级实时数据新鲜度。 |
| **4. 表大小** | 底层原始表巨大（超过 5000 万行）且缺少分区索引。 | 底层表较小（低于 1000 万行）且已完全索引。 |

### B. "冷启动" PDT 加载协议
为防止庞大历史 PDT（尤其是增量 PDT）在初始加载期间因数据库超时、资源耗尽或 slot 限制而崩溃，智能体**必须**执行此缓解协议：

1.  **历史数据封顶（分阶段引入）**：在初始 LookML PDT 定义中，使用条件日期筛选临时封顶历史查询（例如仅查询最近 30 天的数据）。这确保物理表能在几秒内在数据库上成功创建。
2.  **增量回填（引导与扩展）**：初始表创建后，以可管理的批次以编程方式向后扩展历史筛选（例如逐月回填），以构建完整历史，而不触发单个庞大的事务崩溃。
3.  **试运行成本估算**：在构建繁重 PDT 之前，调用 Looker MCP 的 `query` 或 `query_sql` 工具对扫描字节数进行试运行估算，以验证其是否会超出数据库连接的查询限制。
4.  **架构卸载（ELT 外包）**：如果历史数据集过于庞大，无法在 Looker 的 PDT 层内编译或回填，智能体**必须**指示开发者将物化卸载到数据库仓库层（使用 dbt、计划查询或数据库物化视图），并将 Looker 映射为标准只读视图。

## 4. LookML 语义重构规则

优化语义建模层可消除编译器驱动的冗余，并确保数据库仅处理所需的最少数据。

*   **消除对称聚合**：确保准确声明连接关系（`relationship`）。如果一个连接被定义为 `many_to_one` 但实际表现为 `one_to_many`，Looker 的编译器会在 SQL 中注入昂贵的 `_distinct` 聚合函数（例如 `SUM_DISTINCT`、`AVG_DISTINCT`），导致严重的性能下降。
*   **连接剪枝**：构建探索时，使 Looker 仅连接用户所选字段实际查询的表。利用 `required_joins` 参数严格控制连接路径。
*   **禁止 SQL 中的繁重 Liquid 循环**：在 `sql:` 参数中编写会编译成庞大 SQL `CASE WHEN` 链的复杂 Liquid 条件循环是严格**禁止**的。这些链无法被数据库引擎索引，会导致全表扫描。请用干净的 LookML 维度或预计算的 PDT 列替换它们。

## 5. Looker CLI 与 MCP 诊断矩阵

为诊断查询性能并运行执行计划，AI 智能体**必须**利用 Looker CLI 或 Looker MCP server。对于程序化的数据库内省，优先使用 Looker MCP。

| 性能操作 | Looker CLI 命令 | Looker MCP 工具 |
| :--- | :--- | :--- |
| **获取生成的 SQL** | `looker-cli api query query <id> --fields sql` | `query(query_id)` 或 `query_sql` |
| **运行查询（测试）** | `looker-cli api query run_query --query_id <id>` | `query` 或 `run_dashboard` |
| **检查查询状态** | `looker-cli api query query_task ...` | `health_pulse` 或 `health_analyze` |
| **数据库内省** | `looker-cli api metadata connection_columns <conn> --schema_name <schema>`<br>*(另见：`connection_tables`、`connection_schemas`、`connection_databases`)* | `get_connection_table_columns`<br>*(另见：`get_connection_tables`)* |
| **LookML 编译检查** | `looker-cli project validate <id>` | `health_analyze` |

## 6. AI 智能体执行与子智能体委托准则

为优化执行速度、防止 token 膨胀，并避免在你的智能体环境中触及轮次或上下文上限，请遵循以下执行策略：

### 1. 并行查询剖析与上下文隔离（强制）
诊断多个缓慢的仪表板查询会产生庞大的 SQL 语句、数据库执行计划和 JSON 负载。为保持主开发者对话干净且具成本效益，主智能体**必须**委托诊断工作：
1.  **识别慢图块**：编录目标仪表板上所有缓慢的可视化图块。
2.  **生成 SQL 剖析器子智能体**：对于每个识别出的缓慢探索或图块，生成一个专门化的"SQL 剖析器子智能体"以并发运行。
3.  **子智能体诊断任务**：
    *   通过 Looker MCP 获取生成的 SQL。
    *   直接对目标连接执行 `EXPLAIN` 或 `EXPLAIN ANALYZE` 查询。
    *   解析执行计划以识别确切的瓶颈（例如全表扫描、缺少索引、对称聚合）。
    *   编制一份**精简性能报告**，内容精确包含：
        *   有问题的 SQL 片段。
        *   识别出的瓶颈。
        *   确切的、可执行的 LookML 补救措施（例如添加缓存 datagroup、修正连接关系或创建增量 PDT）。
    *   将精简后的发现报告回主智能体并自行终止。
4.  **精简整合**：主智能体仅接收来自子智能体的浓缩、高度可执行的报告，并协调重构工作，使主对话完全不含原始数据库计划转储。

### 2. 精准修改规则（不做完整重写）
为保护开发者注释、保留自定义维度并优化 API token 效率，智能体**必须**遵守以下精准编辑协议：
*   **禁止完整重写**：在对*现有* LookML 文件进行任何性能重构或调优迭代期间，智能体**不得**从头重写、重新生成或重建整个文件。
*   **定向块替换**：智能体**必须**执行精准的局部块替换（例如查找替换、行定向编辑或定向工具调用），以*仅*修改需要优化的特定连接、datagroup 或 SQL 参数。
*   **保留**：不相关的维度、度量、探索连接以及开发者编写的注释**必须**完全保持不动。
