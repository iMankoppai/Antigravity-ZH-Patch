# Arize 合规审计技能

当用户想要**审计其 AI 智能体或 LLM 应用的监管合规性**时使用本技能。该技能扫描代码仓库以查找合规缺口，交叉引用 Arize 埋点的审计追踪覆盖情况，并生成一份带有可选整改的定制清单。

**触发词：** "audit my app for compliance"、"EU AI Act requirements"、"NIST AI RMF checklist"、"GDPR for AI"、"is my AI app compliant"、"compliance checklist"、"regulatory audit"、"ISO 42001"、"AI management system"、"AIMS certification"。

## 免责声明

**在做任何其他事情之前，先将本免责声明原文呈现给用户：**

---

> ⚠️ **法律免责声明**
>
> 本审计**仅供参考**，**不**构成法律意见或完整的合规评估。它基于公开可得的监管框架识别常见的技术模式和缺口，但无法评估贵组织具体的法律义务、合同承诺、数据处理协议或运营流程。
>
> **请勿将本输出作为合格法律顾问意见的替代品。** 监管合规是一项复杂、因司法辖区而异且依赖于具体事实的判定。对于具有约束力的评估，请务必咨询合格的律师或合规专家。

---

## 核心原则

- **优先检查而非修改**——在建议更改之前先理解代码仓库。
- **务实而非法律**——产出开发者可执行的条目，而非法律意见。
- **针对司法辖区和用例量身定制**——聊天机器人与招聘工具的义务不同。不要倾泻整个监管框架。
- **交叉引用埋点**——合规需要审计追踪；检查 Arize 追踪是否捕获了监管机构所期望的内容。
- **提供整改，始终确认**——在呈现清单后，提出可实施具体的修复，但未经用户明确确认绝不修改代码。
- **保持输出简洁且面向生产**——除非被要求，否则不要生成额外的文档或摘要文件。
- **绝不嵌入字面凭据值**——始终引用环境变量。绝不要让用户把机密粘贴到编码智能体聊天中。

## 阶段 0：框架选择与用例

在扫描代码之前，确定适用哪些合规框架。

### 步骤 1 — 框架选择

使用 `AskUserQuestion` 工具询问用户哪些框架适用。**不要推断或自动选择**——始终明确询问。

询问：

```
Which compliance frameworks should this audit cover?
Select all that apply (reply with numbers, e.g. "1, 3"):

1. EU frameworks — EU AI Act, GPAI Code of Practice, GDPR
   (choose if end-users or data subjects are located in the EU)

2. US frameworks — NIST AI RMF, state laws (Colorado AI Act, NYC LL144),
   HIPAA (if processing health data)
   (choose if operating in the United States)

3. ISO 42001 — International AI Management System standard
   (choose if pursuing ISO 42001 certification, operating globally,
   or wanting an internationally recognised baseline)

You can select any combination. If unsure, select all that seem relevant
and we can narrow down during the audit.
```

根据选择：
- **选择 1**——适用 EU AI Act、GPAI Code of Practice、GDPR。参见 [references/eu-ai-act-gpai.md](references/eu-ai-act-gpai.md)。
- **选择 2**——可能适用 NIST AI RMF、Colorado AI Act、NYC LL144、HIPAA。参见 [references/us-ai-compliance.md](references/us-ai-compliance.md)。
- **选择 3**——适用 ISO 42001 AIMS 控制项。参见 [references/iso-42001.md](references/iso-42001.md)。注意：ISO 42001 是一套组织级管理体系——审计将仅覆盖可在技术上审计的控制项；纯组织性的条款（领导层评审、内部审计）将单独标注。
- **选择多个**——所有选中的框架均适用；审计覆盖各项要求的并集，并在框架重叠处进行交叉引用。

### 步骤 2 — 确定用例类别

使用 `AskUserQuestion` 工具询问：**你的 AI 应用是做什么的？**

- **通用聊天机器人 / 助手**——有限风险（EU），一般义务（US）
- **招聘 / HR**——高风险（EU 第 6 条、附件 III）；适用 Colorado AI Act；若在 NYC 则适用 NYC LL144
- **医疗健康**——高风险（EU）；若处理 PHI 则适用 HIPAA
- **信贷 / 金融**——高风险（EU）；适用 Colorado AI Act
- **教育**——高风险（EU）
- **内容生成**——有限风险（EU 第 50 条透明度）；一般义务（US）
- **GPAI 模型提供方**——适用 GPAI Code of Practice（EU）

### 步骤 3 — 确定风险等级

根据用例和所选框架：
- **选择了 EU**：按照 [references/eu-ai-act-gpai.md](references/eu-ai-act-gpai.md) 分类为不可接受 / 高 / 有限 / 极低
- **选择了 US**：分类为高风险（按 Colorado AI Act 属于重大决策）或一般
- **选择了 ISO 42001**：风险等级并非 ISO 42001 中的正式分类，但需注明系统是否属于高风险影响（这会提升影响评估和偏见控制项的优先级）

### 阶段 0 输出

呈现一份简要摘要：

```
Frameworks selected: {EU / US / ISO 42001 / combination}
Use case:            {category}
Risk tier:           {EU tier if applicable} / {US tier if applicable}
Applicable:          {list of specific regulations and standards}
ISO 42001 note:      {if selected} Audit covers technically-auditable controls only;
                     organisational clauses will be flagged but not code-audited.
```

然后直接进入阶段 1。

## 阶段 1：代码仓库审计（只读）

**在此阶段不要编写任何代码或创建任何文件。**

系统地扫描代码仓库，在七个领域查找合规证据和缺口。对于每个领域，运行所列的检索并记录发现。

### A. 透明度与披露

**要查找的内容：**
- 披露 AI 参与的用户面向字符串：在 UI 模板、API 响应和用户面向代码中检索 `AI`、`artificial intelligence`、`automated`、`bot`、`machine learning`、`generated by`、`powered by` 等术语
- 内容标注：AI 生成输出（文本、图像、音频）上的标记
- 代码仓库中对服务条款、隐私政策的引用

**值得关注的信号：** 用户面向代码中缺少任何 AI 披露，尤其是当应用生成内容或给出推荐时。

### B. 数据保护与隐私

**要查找的内容：**
- 代码中的 PII 字段名：提示、上下文或检索文档中的 `email`、`phone`、`ssn`、`social_security`、`date_of_birth`、`address`、`name`
- 追踪 span 属性中的 PII：检查 `input.value` 或 `output.value` 是否可能在未脱敏的情况下将个人数据发送到 Arize
- 同意机制：`consent`、`opt-in`、`opt-out`、`gdpr`、`ccpa` 引用
- DPIA 或隐私评估引用
- 数据保留和删除处理器
- 数据主体权利：`right_to_access`、`right_to_erasure`、`data_subject_request`、`data_protection_officer`

### C. 安全

**要查找的内容：**
- 提示注入防御：输入验证、护栏库（`guardrails-ai`、`nemo-guardrails`、`rebuff`、`lakera`）、内容过滤、系统提示保护
- 数据丢失防护：返回用户前对输出进行扫描、敏感数据检测
- 工具/函数调用控制：权限边界、允许列表、工具执行的沙箱隔离
- AI 端点上的速率限制和身份认证
- 硬编码机密：源文件中的 `api_key`、`secret`、`password`、`token` 字面值（而非环境变量引用）

### D. 测试与评估

**要查找的内容：**
- 偏见与公平性测试：对人口统计均等、影响比、公平性指标的引用
- 红队或对抗性测试套件：提示注入测试、越狱测试
- 评估框架：Arize 评估器、自定义评估脚本、基于 `pytest` 的评估、实验基础设施
- A/B 测试或模型比较基础设施

### E. 文档

**要查找的内容：**
- 模型卡：`MODEL_CARD.md`、`model_card.json`、`model_card.yaml` 或类似文件
- 系统架构文档
- 提示和模型更新的变更日志或版本追踪
- 事件响应文档

### F. 监控与可观测性

**要查找的内容：**
- Arize 追踪配置：`arize-otel`、`register()`、`TracerProvider`、`opentelemetry`、`openinference` 导入
- 若存在追踪，检查覆盖情况：
  - 所有 LLM 调用均被追踪（而非仅部分）
  - 用于对话连续性的会话 ID
  - 用于支持数据主体请求的用户 ID
  - 错误追踪和异常 span
- 告警和漂移检测配置
- 追踪保留配置

### G. 供应商管理

**要查找的内容：**
- 第三方 AI API 使用：OpenAI、Anthropic、Google、Azure、Bedrock、Cohere 的导入或客户端实例化
- 模型版本管理：是否固定了具体的模型版本（例如 `gpt-4-0613`），或使用了 `latest` / 无版本标识符
- 提供方之间的回退和故障转移逻辑

### 阶段 1 输出

呈现一份两部分报告：

**第 1 部分——摘要表**

| 领域 | 发现的证据 | 识别出的缺口 | 评级 |
|---|---|---|---|
| A. 透明度 | {findings} | {gaps} | 合规 / 部分合规 / 不合规 / 不适用 |
| B. 数据保护 | {findings} | {gaps} | ... |
| C. 安全 | {findings} | {gaps} | ... |
| D. 测试 | {findings} | {gaps} | ... |
| E. 文档 | {findings} | {gaps} | ... |
| F. 监控 | {findings} | {gaps} | ... |
| G. 供应商管理 | {findings} | {gaps} | ... |

**第 2 部分——缺口详情（每个"不合规"或"部分合规"评级都必须提供）**

对于每个评级为"不合规"或"部分合规"的领域，撰写一个专门的小节，包含：

1. **确切的代码路径**——文件路径、行号，以及显示缺口所在位置的相关代码片段。不要转述；引用实际代码。
2. **为何在本特定应用中重要**——结合本代码仓库的上下文解释具体风险（例如哪些工具可能被滥用、哪些数据流被暴露、攻击者或监管者会发现什么）。
3. **缺失了什么**——精确描述本应存在但尚不存在的控制或代码（例如"一个在 OTLP 导出器触发前对 `user_email` 进行哈希处理的 span 属性处理器"，而不只是"添加 PII 脱敏"）。

每个"不合规"/"部分合规"领域至少一个小节。不要省略此部分——它是审计对工程团队的主要价值所在。

然后直接进入阶段 2。

## 阶段 2：合规清单

使用阶段 1 的发现和 [references/compliance-checklist-template.md](references/compliance-checklist-template.md) 中的模板，生成一份**量身定制的合规清单**。

### 清单生成规则

1. **仅包含相关章节。** 如果用户仅涉及美国，跳过 GDPR 专属条目。如果不涉及医疗，跳过 HIPAA。如果不在 NYC 招聘，跳过 LL144。
2. **标注阶段 1 的条目。** 已找到证据的条目：标注为 `Compliant`。存在缺口的条目：标注为 `Non-compliant` 并给出具体的整改建议。
3. **正确确定优先级。** 关键 = 执法风险或系统禁止。高 = 法规要求。中 = 框架推荐。低 = 最佳实践。
4. **整改要具体。** 不要说"实施输入验证"，而要说"添加 `guardrails-ai` 之类的护栏库，按你的内容政策校验 LLM 的输入和输出"。
5. **包含模板中的埋点交叉引用表。** 如果未设置 Arize 追踪，将其标记为关键缺口——EU 第 12 条和 NIST MAN-2.1 要求审计追踪。

### 最终报告

呈现一份合并后的单一报告，包含四个部分：

**第 1 部分——审计范围（阶段 0 摘要）**
- 所选框架、用例、风险等级、适用法规

**第 2 部分——代码仓库发现（阶段 1 摘要表）**
- 领域表（A–G），包含证据、缺口和评级

**第 3 部分——缺口详情（阶段 1 展开）**
- 每个"不合规"或"部分合规"领域一个小节，每个包含：确切的文件路径和行号、引用的代码片段、针对本应用的风险说明，以及关于缺失内容的精确描述。本部分为强制项——绝不省略。

**第 4 部分——合规清单（阶段 2）**
- 带有状态和整改建议的定制清单、埋点交叉引用表、优先级摘要，以及建议的后续步骤

当用户要求提供报告文件时，将一份包含全部四个部分的 Markdown 文件写入 `/tmp/<app-name>-compliance-audit-<YYYY-MM-DD>.md`。

在呈现报告后，提供阶段 3 的整改。

## 阶段 3：整改（可选）

在呈现清单后，提出可实施具体的修复。**在做出任何更改之前，始终使用 `AskUserQuestion` 工具进行确认。**

### 整改类别

**添加依赖**——提出可安装：
- 用于输入/输出校验的护栏库（例如 `guardrails-ai`、`nemo-guardrails`）
- PII 检测/脱敏包（例如 `presidio-analyzer`、`scrubadub`）
- 内容安全分类器

**插入代码**——提出可添加：
- 用户面向输出（模板、API 响应）中的 AI 披露字符串
- 导出到 Arize 之前对 span 属性的 PII 脱敏过滤器
- AI 端点上的输入校验/清理
- 追踪 span 上的用户 ID 属性，以支持数据主体请求

**创建文档模板**——提出可搭建：
- 模型卡模板（含标准章节的 Markdown 文件）
- 事件响应计划模板
- 数据处理记录模板

**配置监控**——提出可通过相关技能设置：
- 用于偏见检测和内容安全的 Arize 评估器（通过 `arize-evaluator` 技能）
- 用于审计追踪覆盖的追踪（通过 `arize-instrumentation` 技能）

### 整改规则

- 将每项整改呈现为**离散、可确认的操作**。绝不批量应用更改。
- 准确展示将要更改的内容（文件、代码差异概念），然后使用 `AskUserQuestion` 工具在应用前获取确认。
- 遵循现有代码风格和项目约定。
- 绝不嵌入凭据——始终使用环境变量。
- 测试更改后应用仍能构建。

## 技能编排

当阶段 1 或 2 中识别的缺口需要其他 Arize 技能的能力时，提出可调用它们。**在调用另一个技能之前，始终使用 `AskUserQuestion` 工具进行询问**，并解释其与合规缺口的相关性。

| 缺口 | 要调用的技能 | 原因 |
|---|---|---|
| 无追踪 / 审计追踪不完整 | `arize-instrumentation` | EU 第 12 条和 NIST MAN-2.1 要求事件日志；Arize 追踪可提供此能力 |
| 无偏见或安全评估 | `arize-evaluator` | 创建用于公平性、内容安全或质量监控的 LLM-as-judge 评估器 |
| 需要导出追踪作为合规证据 | `arize-trace` | 导出 span 用于监管文档或事件调查 |
| 高风险决策需要人工审核 | `arize-annotation` | 按 EU 第 14 条设置用于人工监督的标注队列 |
| 需要深度链接以分享合规证据 | `arize-link` | 生成指向特定追踪、span 或评估的 URL，供利益相关者审阅 |

## 埋点交叉引用

如果已设置 Arize 追踪，验证其是否满足合规要求：

| 合规需求 | 所需的追踪数据 | 要检查的内容 |
|---|---|---|
| AI 决策的审计追踪 | 所有带输入/输出的 LLM span | 验证所有 LLM 客户端调用均已埋点，而非仅部分 |
| 数据主体访问请求 | span 上的用户 ID 属性 | 检查 `user.id` 或自定义用户标识符属性 |
| 追踪中的 PII | `input.value`/`output.value` 中的敏感数据 | 检查 PII 是否未经脱敏通过——若是则标记 |
| 事件调查 | 带完整上下文的错误 span | 检查 span 上的异常追踪和错误状态 |
| 保留要求 | 追踪数据保留至所需期限 | EU：适当期限（高风险至少 6 个月）；HIPAA：6 年 |
| 偏见监控 | 人口统计或分组属性 | 检查能支持公平性分析的元数据属性 |

如果**未**设置 Arize 追踪，这是一个重大的合规缺口。提出："是否需要我运行 `arize-instrumentation` 技能来设置审计追踪埋点？监管框架（EU AI Act 第 12 条、NIST AI RMF MAN-2.1）要求 AI 系统具备事件日志。"
