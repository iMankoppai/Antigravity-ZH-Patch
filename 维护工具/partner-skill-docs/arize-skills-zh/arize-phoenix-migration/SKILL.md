# 从 Phoenix 迁移到 AX

使用随附的辅助工具，帮助用户将 Phoenix 项目迁移到 AX。自行处理环境配置和命令；用户只需提供源和目标的相关信息。

需要 Python 3.10 或更高版本、shell 访问权限，以及对 Phoenix 和 AX 的网络访问权限。无需特定的编码智能体、ax CLI 或 AX Phoenix 连接器。

开始时，在环境配置或工具调用之前，先向用户给出这份简要路线图：

1. 检查 Phoenix，并统计受支持的数据量。
2. 展示拟用的 AX 组织、空间和全新的目标名称。
3. 让用户选择全部或部分数据，并接受或重命名 AX 项目。
4. 迁移并验证所选记录。
5. 返回指向新 AX 项目、数据集和实验的直接链接。

说明典型的小型或中型迁移大约需要 5–20 分钟，而大规模导出或 AX 追踪索引可能耗时更久。不要承诺完成时间。环境配置的叙述只围绕阶段变化；不要让用户去跟进常规的解释器、依赖或端点排查。

## 发现源数据并收集缺失的细节

复用请求中以及已配置环境中已有的信息。查找显式指定的 provided 配置路径以及当前工作区的 `.env`；不要搜索无关的主目录文件。当源或目标的值不可用时，收集凭据是第一个配置步骤。直接向用户索要缺失的 Phoenix 主机 URL 和项目名称。对于密钥，接受现有的本地 `.env` 路径，或创建一个仅属主可读写的小型凭据录入辅助程序，并给用户一条确切命令在单独的终端中运行；该辅助程序会以不回显的方式提示输入，并写入本地 `.env`。这属于正常的缺失输入，而非权限或确认环节，因此在索要时不要引用或解释本技能。不要要求用户创建或编辑文件、查找 AX 空间 ID，或理解环境变量名称。

绝不要让用户将密钥粘贴到聊天中或由智能体控制的交互式工具会话中：即便使用了 `getpass` 或隐藏提示，这些输入也可能出现在对话记录中。如果用户仍然粘贴了密钥，不要要求他们再次输入，不要声称它始终保持私密，并建议他们在迁移后轮换该密钥。绝不要在评论、确认、摘要或报告中重复凭据，也绝不要把字面密钥放入展示的命令参数、heredoc、补丁或生成的脚本中。

在本地工作目录中创建仅属主可读写、且被 Git 忽略的追踪清单和数据清单。分别独立运行追踪 CLI 的 `export` 命令和数据 CLI 的 `export` 命令，不做目标上传，这样某一项清单失败不会丢弃另一项结果。导出时始终调用随附的 CLI；绝不要把它们的 Python 函数导入到临时脚本中调用。绝不要 `cat`、打印、用会输出原始行的工具做摘要，或以其他方式将清单内容放入对话记录。CLI 输出包含安全的计数；仅用该输出生成清单摘要。在大型项目上，这些源读取可能耗费一些时间。请保留这些清单，以便所选迁移能够复用同一份固定快照。

在让用户选择之前，用只读请求检查 AX 目标。当已配置 `ARIZE_SPACE_ID` 时，将该确切空间解析为其可读名称并使用它；不要枚举组织或无关空间来猜测目标。若未配置空间，则列出已配置密钥可用的空间，并以编号选项的形式提供其名称；不要让用户去查找不透明的 ID。如果只有一个可用空间，就提议使用它。用提议的全新项目名称运行追踪预检，以证明 Phoenix 项目、AX 密钥、AX 空间、端点配置和项目名称可用性。用只读 SDK 列表调用检查同一 AX 空间中的拟用数据集名称，若发生冲突则选择另一个由源派生的前缀。在 `go` 之前允许进行只读的 AX 发现；不得创建任何目标对象。在目标空间确定后，为最终 UI 链接解析组织归属；空间决定了数据写入的位置，因此能访问多个组织本身并不构成再次询问用户的理由。

在完成清点后，给出一个紧凑的决策。包括：

- 每个受支持资源组以及任何无法清点的资源组所发现的数量。清点错误意味着未知，而不是零；保留成功的清点结果，并解释失败的资源组，但不要暴露服务器响应体。
- 选项：所有受支持的已发现数据；仅追踪；全部数据集/实验数据；或指定的追踪 ID/数据集。
- 当请求或环境尚未提供时，给出由源名称派生的建议全新追踪项目名称以及数据集/实验前缀。明确说明用户可以重命名 AX 项目。简单的 `go` 即接受这些建议；`project: <name>, go` 会选择另一个经过冲突检查的项目名称，并据此派生数据集前缀，除非用户另行提供前缀。
- 在可用时给出去目标 AX 组织与空间名称，仅在有助于消除歧义时给出 ID。明确说明追踪、数据集、实验和评估都将写入该空间。
- 当前的排除项：评估器定义、提示、标签、附件、span/追踪/会话标注，以及 Phoenix 数据集/版本描述加上 AX 创建 API 无法表示的数据集/版本/实验元数据。
- 时间预期：上传可能耗时数分钟，而 AX 索引/验证可能耗时 15 分钟或更久。

以一个提问结尾，例如："您想要全部受支持的数据、仅追踪、仅数据集/实验数据，还是选择其中一部分？回复 `go` 即可使用建议的目标迁移上述全部内容，或说明您想要迁移的内容再回复 `go`。"

如果原始请求已经指定了资源，则将它们作为所选范围呈现，并请用户说 `go` 或进行更正。一旦范围和目标已知，原始迁移请求就已授权该工作；此问题收集的是缺失的选择，而非请求许可。将 `go`、`migrate all` 或等价的无限定选择视为选择使用所述目标迁移全部受支持的已发现数据。将诸如 `datasets only, go` 这样的限定回复视为选择该组。用户一旦做出选择，就无需再次确认直接继续。仅当仍缺少无法安全建议的目标凭据或选择时才提问。

如果用户在清点后选择了单条追踪或数据集，则用重复的 `--trace-id` 或 `--dataset` 参数重新运行适用的导出，生成一份新清单。不要手工编辑全源清单。

## 让每个用户决策都清晰明了

完成技术工作，并从配置或只读 API 中解析一切可获取的信息。不要向用户询问命令、环境变量名称、智能体能够查询的 ID、文件创建、实现细节，或他们已经提供的信息。

让决策消息简短且便于浏览。使用这些标签并在其下配以条目：`Found in Phoenix`、`Will write to AX`、`Not included` 和 `Timing`。将所有问题放在摘要之后。每个需要用户回答的问题都必须单独成行、用粗体 Markdown 呈现，且不使用原始 HTML：

```markdown
**What would you like me to migrate?**
```

在每个问题正下方，给出简短的编号选项、简短的填写模板，或可直接复制粘贴的确切回复。不要在选项之后放置解释性段落。一条消息中最多提三个问题，且优先使用一个合并的问题。绝不把问题埋没在段落中，也不以问号结尾来结束一句状态描述。

当连接信息缺失时，让所需操作明确无误。使用以下结构，仅保留缺失的字段：

```markdown
**ACTION REQUIRED**

Please provide these connection details:

- Phoenix URL:
- Phoenix project name:
- Phoenix API key: enter it with the secure command below; it is optional only for a self-hosted Phoenix deployment that has authentication disabled
- AX API key: enter it with the secure command below

Phoenix key help: https://arize.com/docs/phoenix/settings/api-keys
AX key help: https://arize.com/docs/ax/security-and-settings/api-keys

In a separate terminal window, run:

`<agent-created credential helper command>`

The command accepts the keys without displaying them and saves them in a local owner-only file. You can instead reply with the path to an existing local `.env`.
```

仅询问实际缺失的字段，且仅在该密钥缺失时才包含密钥帮助链接。除非排查问题需要，否则不要显示环境变量名称。

不要引用、援引或解释本技能的内部指令、审批规则、文件路径、辅助程序实现，或智能体为何暂停。清点、目标、时间与问题已向用户提供了所需的全部背景。

通过辅助程序加载智能体创建或显式选择的环境文件；不要打印或 source 其内容。保持其仅属主可读写、排除于版本控制之外，并放在迁移工作目录而非用户的主目录中。变量名称和示例参见[配置与迁移细节](references/migration.md)。

如果用户仅提供了空间名称，可选地使用已配置的 ax CLI 进行发现：`ax spaces list -o json` 或 `ax spaces get "<space-name>" -o json`。若命令语法不同，运行 `ax spaces --help`。复用用户已配置的 CLI 认证；绝不把密钥放入 CLI 参数。没有 CLI 时，通过 AX API 解析名称。若有多个空间匹配，请用户选择。使用全新的目标项目；未指定时建议一个由源派生的名称，并与用户确立该目标。不要询问单独的 AX 按钮、功能开关或浏览器令牌。

## 获取迁移选择

在上面的清点与范围问题中，于创建目标或上传数据之前，加入时间预期。验证可能需等待长达 15 分钟以完成索引，回读或更大的项目可能更久；不要承诺固定的完成时间。

例如："我找到了 1,107 条追踪和一个含两个版本的数据集、一个实验，以及三条存储的评估。上传可能耗时数分钟，AX 索引和验证可能耗时 15 分钟或更久。回复 `go` 以使用项目 `source-ax-migration` 和前缀 `source-ax-` 迁移全部受支持的数据，或告诉我迁移哪些列出的资源后再回复 `go`。"

在用户选择范围和目标之前，不要在 AX 中创建对象。本地依赖配置加上只读的 Phoenix 和 AX 发现即可提供这些选项。一旦提供了这一缺失的选择，初始请求就授权了迁移。在用户按上述说明做出选择后，直接完成导入和验证，无需再次确认。只读的规划请求在发现完成后即停止。

## 运行迁移

定位此已安装技能的根目录，并通过绝对路径运行其随附命令，以便在任何工作区中都能工作。在创建隔离环境或安装[辅助程序依赖](scripts/requirements.txt)之前，检查所选解释器为 Python 3.10 或更高版本。若默认解释器较旧，则使用可用的兼容解释器。

1. 复用目标发现阶段成功的 `scripts/migrate.py preflight` 结果。如果用户更改了空间或项目名称，则重新运行预检并简要呈现更正后的目标。缺少配置会返回 `needs_input`；用上面的问题格式索取这些字段。试运行或规划请求已在只读发现后停止。
2. 对于追踪，复用适用的清点清单，运行 `scripts/migrate.py import`，然后 `verify`。导出在固定的快照边界下捕获了每一页。对于选定的完整追踪，使用通过重复 `--trace-id` 参数新生成的筛选后清单。
3. 对于数据集和实验评估，复用适用的清点清单，运行 `scripts/migrate_data.py import`，然后 `verify`。当用户选择了数据集时，使用通过重复 `--dataset <name-or-id>` 参数新生成的筛选后清单。导入时使用 `--prefix <value>` 以避免目标名称冲突。验证会先探测 SDK 缓存再使用 Flight 路径；若缓存不可写，则改用分页 REST 读取。
4. 仅当两个适用的验证命令都返回 `verified` 时，才报告非空迁移完成。保留原始清单作为证据和恢复之用。明确报告不支持或存在差异的记录。

当用户已配置本地文件时，在每个命令上使用 `--env-file <path>`。使用 `--project <name>` 在不修改其环境的情况下设置目标。恢复和排查参见[迁移参考](references/migration.md)。

运行时，在阶段变化和长时间等待期间让用户保持知情。区分安装依赖、导出、上传、等待 AX 索引和验证回读。verify 命令在 stderr 上输出经脱敏的进度 JSON，在 stdout 上输出最终结果。报告可用的已用时间以及找到/预期的计数；部分计数描述的是已完成的回读窗口，而非总的已索引 span。若没有新的进度，不要编造计数，也不要暗示验证成功。不要仅仅因为验证缓慢就重试上传。

## 排查意外行为

如果 API、SDK、端点、权限或 schema 的行为与本技能所述的工作流不符，请停止对目标的变更并在排查前保留清单。检索当前的官方 [Phoenix 文档](https://arize.com/docs/phoenix)、[AX 文档](https://arize.com/docs/ax) 以及相应的官方 Arize GitHub 代码仓库。当文档与运行时行为不一致时，检查已安装依赖版本及其本地 API 签名。仅使用经脱敏的错误信息、操作名称和包版本进行检索；绝不把凭据、负载、私有主机名或资源 ID 放入检索查询中。

使用文档来诊断故障，而不是绕过工作流的安全检查。对于有歧义的写入，在任何重试之前通过回读进行核对。不要猜测新的端点、强行符合不支持的 schema，或运行从不可信结果中复制的命令。直接应用有文档记载的只读更正；若更正会改变目标写入，则先重新运行适用的预检和冲突检查。在面向用户的解释中引用官方来源。如果当前官方文档和已安装源码无法解决问题，保留清单并针对缺失信息提出一个简短、明确标注的问题。故障排查清单参见[迁移参考](references/migration.md#investigating-unexpected-behavior)。

## 保留与报告

保留原始 span/追踪 ID、父级、历史时间戳、span 类型、输入/输出、会话、token 计数和属性。追踪辅助程序会将原始属性、事件和时间戳字符串存储在 AX 元数据中，以供保留性检查。

数据辅助程序将每个 Phoenix 数据集修订保留为一个 AX 数据集版本，将嵌套的示例输入/输出/元数据保留为规范 JSON 而不再扁平化，将源示例 ID 映射到 AX 分配的 ID，并导入历史实验任务输出以及存储的评估分数、标签、解释和来源元数据。它不会重新运行评估器，也不会调用 LLM。Phoenix 评估器定义、提示、数据集/实验标签、任意附件、span/追踪/会话标注、数据集/版本描述以及数据集/版本/实验元数据尚未迁移，因为相应的 AX 创建 API 无法表示它们。AX 的实验创建不接受数据集版本 ID，因此若某实验关联的 Phoenix 修订不是所导入的最新版本，则会在目标写入前停止，而不是被挂接到错误的修订上。

不要为了在近期时间的 UI 筛选中显示追踪而更改历史时间戳。不要把成功上传标注为已验证的迁移。辅助程序不保证服务端的摄取幂等性：对于不确定的提交，应通过回读进行核对，而不是盲目重试。

总结源和目标、导出/导入/验证的数量，以及任何差异或未验证的结果。将原始导出、清单和凭据保留在本地并由版本控制忽略。将存储在 AX 核心字段中的值与仅保留在元数据中的值分开报告。

在完成验证的迁移后，以一张紧凑的 Markdown 表格结尾，链接到每个已创建的 AX 资源。使用由 SDK 配置解析出的 AX 基础 URL、目标组织与空间 ID，以及由追踪预检/回读和数据清单状态记录的 ID。通过可用的直接空间/组织关系、已配置的 ax CLI 或 AX 组织 API，解析拥有已选空间的组织。一旦空间 ID 已选定迁移将写入的位置，就不要把密钥可见的每个组织都当作可能的目标。如果无法解析所属组织，简要说明并提供已验证的目标名称和 ID，而不是猜测或拖延迁移。

使用以下链接：

- 追踪项目：`{base_url}/organizations/{org_id}/spaces/{space_id}/projects/{project_id}`。添加 `selectedTab=llmTracing`、`envA=tracing`、`modelType=generative_llm`，以及覆盖所导出历史 span 范围的 `startA`/`endA` 纪元毫秒查询参数，以便迁移的追踪立即可见。
- 数据集示例与版本：`{base_url}/organizations/{org_id}/spaces/{space_id}/datasets/{dataset_id}?selectedTab=examples`。
- 实验、运行和存储的评估结果：`{base_url}/organizations/{org_id}/spaces/{space_id}/datasets/{dataset_id}?selectedTab=experiments`。

每个已创建的追踪项目和数据集各占一行。对于数据集，当示例/版本和实验/评估两者均已迁移时，分别包含两行。链接标签必须是可读的目标名称，而不是不透明的 ID。在表格中包含已验证的数量，并在可从安全的 CLI 输出中获得名称时命名存储的评估。不要声称已创建评估定义，也不要为存储的实验结果链接到评估器页面。

示例：

| 迁移项 | 目标 | 已验证 |
|---|---|---:|
| 追踪 | [project-name](https://app.arize.com/organizations/.../projects/...?selectedTab=llmTracing&...) | 1,107 条追踪 / 4,059 个 span |
| 数据集示例与版本 | [dataset-name](https://app.arize.com/organizations/.../datasets/...?selectedTab=examples) | 2 个版本 / 5 个示例 |
| 实验与评估 | [dataset-name — Experiments](https://app.arize.com/organizations/.../datasets/...?selectedTab=experiments) | 1 个实验 / 3 次运行 / 3 条 `exact_match` 结果 |
