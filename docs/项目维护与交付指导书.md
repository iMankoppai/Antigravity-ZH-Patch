## 4. 第二阶段：建立不会误翻内容的本地化维护流程

### 4.1 每个漏译先分四类

| 文本类型 | 修复位置 | 示例 |
|---|---|---|
| 固定 UI 文字 | `dictionaries.json` | 按钮、菜单、设置说明 |
| 带变量的 UI 模板 | 受范围限制的模板规则 | 思考耗时、任务数量、点击元素状态 |
| DOM 被拆分的 UI 标签 | 专门的结构适配函数 | 独立时间节点、图标与文字混排、动作加文件目标 |
| 用户或模型内容 | 保护规则 | AI 回答、思考内容、代码、命令、文件名、任务标题 |

截图中的症状通常同时涉及第二、第三类。给词库追加 `Analyzed` 只能解决一部分表现；如果选择器保护范围过宽，UI 状态根本不会进入翻译流程；如果放宽过头，又会误改正文。

### 4.2 一条修复的标准流程

1. 采集原文、所在控件、最小 DOM 结构、客户端版本和触发步骤。优先只保存结构，避免保存完整会话内容。
2. 判断它是固定词、动态模板、拆分节点还是内容。记录“为何属于 UI”。
3. 先写失败用例，再修改最小必要范围。针对状态前缀，同时添加“同名文件”和“正文含相同文字”的保护用例。
4. 核验已有保护根：输入控件、正文、思考正文、代码区、终端输出。保护规则优先于通用字典和正则匹配。
5. 只有经过结构确认的状态标签才能启用例外；不能为了命中标签而放行整个聊天容器。
6. 遇到未知 DOM 结构时保留原文，并记录适配缺口；不退回整页扫描并强制替换。
7. 检查动态刷新、节点复用、翻译恢复。尽量修改既有文本节点，不重建用户内容节点，不覆盖整块 `innerHTML`。

当前关键代码定位：`translate.js` 中的 `statusRegion`、`statusPayload`、`elapsedStatus`、`translateStatusLabel`、`translateElapsedContainer`、`isConversationContent`、`translateTextNode`、`restoreNode`。当前约在 452–600 行和 967 行附近，后续改动后用函数名定位。

### 4.3 术语、占位符和例外

固定核心术语：Discard＝放弃，Quota＝额度，Sidebar＝侧边栏，Pane＝面板，Repository＝代码仓库，Plugin＝插件。扫描混用词时应结合英文原文和上下文，不能把所有出现“丢弃”等字样的中文机械替换。

占位符检查应比较**多重集合**：种类、名称、出现次数都一致。检测 `{0}`、`{name}`、`%s`、`${var}`、`{{count}}` 等时，先识别长形式，再识别短形式，避免把 `{{count}}` 误拆成 `{count}`。确有格式语法或字面量花括号例外时，建立明确例外表及原因，不能静默跳过。

对 `key === value` 建立逐条保留说明，例如产品名、主题名、快捷键和语言标识。新条目没有说明时进入人工复核。标点规则针对翻译后的 UI 文案；代码、路径、命令、占位符原样保留。

**待实现：**增加受版本管理的词条来源清单，例如 `localization/dictionary-context.json`。它是辅助证据，不替换运行时词库。建议结构如下：

```json

  "Analyzed": {

    "surface": "tool activity file row",
    "clientVersion": "2.21.1",

  }

```

### 4.4 正则与性能规则

- 用完整匹配、明确边界、有限长度和简单字符集合；避免重叠重复、嵌套量词和对任意正文的贪婪捕获。
- 拼接短语优先解析确定的 UI 结构。文件路径、被引号包裹的原始命令和用户标题不要继续交给通用词条处理。
- 测试超长近似匹配输入、缺少结束引号、长数字串、重复前缀和大量连续 DOM 变更。
- 用独立进程或可终止的 Worker 设置超时；同一 JavaScript 线程上的计时器无法中断正在回溯的正则。
- 记录测试机器、输入长度、测试数量和最长耗时。先建立正常基线，再设置合理阈值，不用跨机器固定极小毫秒数造成假失败。
- MutationObserver 只处理相关变更，避免每次扫描整页；缓存和恢复机制须验证节点内容更新后仍正确。

**本阶段完成条件：**每个修复都有 UI 命中证据和内容不变证据；占位符与术语检查无未解释异常；未知结构不会触发大范围翻译。

### 5.3 必须补齐的测试

**渲染边界：**UI 状态前缀翻译；AI/思考正文中的同词不变；用户输入和终端不变；目标名是 `Read` 或 `Analyzed` 不变；引号中的命令不变；时间拆分节点变化正确；跨节点复用不残留；恢复原始英文；属性翻译范围一致。

**深层界面：**权限申请、外部工具批准、沙箱提示、鉴权失败、上下文压缩、Rules demoted、Branch/Share、搜索无结果、空列表、右键菜单。分别建立固定文字或模板用例；对无法在测试环境触发的项保留手工验收入口。

**ASAR 结构：**空文件、普通文件、4 MiB 边界前后、多层目录、`unpacked`、`link`、无效偏移、截断归档、缺少注入目标、重复锚点、已有内核、连续安装、选项变化、模拟写入中断和恢复版本不匹配。

**交付资源：**词库与生成包内容逐项相等；生成包内脚本等于源码；编译后的 EmbeddedResource 等于预期资源；ZIP 解压后的 EXE 等于发布 EXE；安装归档内的 bundle 等于这次发布资源。

注意：反射检查普通编译 DLL 的资源是有价值的，但不能单独证明最终单文件 EXE 打包正确。还需要确保 EXE 来自同一次 publish，必要时提供发布程序的只读资源校验接口或单文件启动自检，并核验包内 EXE 的哈希。

### 5.4 CI 接入顺序

**待实现：**Windows 检查任务。先实现本地统一入口，再让 CI 调用相同入口，避免 CI 和本地执行不同脚本。

顺序固定为：依赖检查 → 词库质量 → 脚本语法 → `重建汉化内核.js --check` → 浏览器回归 → 合成 ASAR 测试 → 编译 → 资源核验 → 测试包验证。

固定已验证的 .NET/Node 版本；如采用 `global.json`，先在干净环境验证对应 SDK 可安装。CI 不安装到开发者客户端，不关闭实际应用，不自动推送、不发布未验收的交付包。可上传脱敏测试结果和合成夹具。

**本阶段完成条件：**新克隆工作区无需历史 `work/adapt-*` 即可验证当前源码；必需失败可阻断后续流程；历史测试与当前测试明确区分。

## 6. 第四阶段：加固 ASAR 安装、更新和回滚

当前 `AsarCleanPatcher.cs` 已拒绝覆盖运行中的客户端，对 packed/unpacked/link 作区分，并生成完整性块信息。仍需加固以下机制；这部分属于后续代码改造。

### 6.1 用版本与哈希识别备份

当前固定 `app.asar.bak` 不能证明它属于正在安装的官方版本。后续增加备份清单，至少记录：官方产品版本、平台架构、原 ASAR SHA256、备份路径、创建时间、补丁版本、所需外部资源描述。

安装前：读取客户端版本 → 计算当前归档哈希 → 判断原版或已知补丁版 → 核对备份 → 核对适配规则。无法识别时停止写入，并输出明确的适配缺口。

官方升级后：为新官方归档建立新备份，不覆盖旧备份。恢复英文时，仅选择与当前客户端版本、基线哈希相符的备份。不能把 2.21.1 的 ASAR 恢复到其他版本目录。

### 6.2 给字符串注入设置命中数量

当前引擎包含多处 `String.Replace` 和标记判断。后续每个注入点都应定义预期命中数与已安装状态，例如“原始锚点恰好 1 处，或已安装标记恰好 1 处”。零命中、多命中或两种状态同时存在都拒绝写入。

为每个支持版本记录实际验证过的锚点、目标文件和预期结构。存在 `unpacked` 或 `link` 的目标不能按普通 packed 文件注入；拒绝结果应说明原因。不要为未知版本绕过完整性机制或随意重定位模块。

### 6.3 将写入分为准备、验证、提交

建议状态流程：

```text
确认客户端关闭
  → 校验版本、基线、备份和注入点
  → 在同一文件系统写临时归档
  → 重新读取临时归档并完整验证
  → 记录安装清单
  → 执行可恢复的提交
  → 重新读取最终文件并验证
  → 启动客户端并验收
```

临时归档验证包括：头部长度、所有 packed 范围、偏移及大小、完整性块、`unpacked`/`link` 元数据保留、外部依赖存在、目标 bundle 内容，以及实际改动列表等于计划改动列表。不能把“已经写出了临时文件”当成验证通过。

恢复也使用相同的临时文件与校验流程，避免当前直接覆盖路径留下半写状态。Windows 文件替换机制须明确其保证边界，并通过锁文件、磁盘空间不足和异常中断测试，不宣称未经验证的断电原子性。

### 6.4 清理旧文件先证明归属

当前精确文件名清理比通配符稳妥，但 `common.ps1`、`launch.ps1` 等名称不能单独证明是本项目创建的。

后续以安装清单、已知哈希或本项目标记确认归属；匹配失败则保留并提示。清理前验证规范化绝对路径仍在预定安装目录中，拒绝路径逃逸。只清理本次操作可证明拥有的对象。

### 6.5 更新与异常处理

| 情况 | 应做什么 | 完成证据 |
|---|---|---|
| 客户端仍运行 | 要求保存草稿，正常退出；用户授权后再关闭并重启 | 进程检查通过，不依赖强杀实现常规安装 |
| 官方版本变化 | 建立新基线和适配检查；旧版补丁停止自动写入 | 新版本清单、哈希、隔离测试和现场验收 |
| `unpacked` 或 `link` 引用异常 | 保留结构并报告缺失，停止提交 | 副本重封包验证，外部依赖未误装入归档 |
| 临时归档校验失败 | 删除或保留仅属于本次操作的临时文件供分析 | 原归档哈希不变，失败原因可定位 |
| 提交后启动失败 | 使用匹配备份回滚，保留日志 | 恢复后归档哈希等于对应官方基线 |
| 备份版本不匹配 | 拒绝恢复，重新取得对应官方基线 | 无错误版本覆盖 |

**本阶段完成条件：**未知版本不写入；失败不损坏原归档；恢复不会混用版本；外部依赖保留；清理不会仅凭通用文件名删除用户文件。

## 7. 第五阶段：统一生成和发布流程

### 7.1 先解决双生成入口

当前 `维护工具/重建汉化内核.js` 保留现有包装器，而 `scripts/build-bundle.js` 生成完整包装器。建议提取一套受审查的包装器模板和生成实现，另一入口仅调用它，最终只维护一份规则。

统一入口需要支持：生成、只检查、语法检查、资源内容比较和明确退出码。生成操作应确定且可复现。改动后两次生成的字节必须一致，`--check` 不修改文件。

普通词库或运行时修复可以按当前入口重建：

```powershell
Set-Location -LiteralPath 'D:\DSH\Antigravity ZH'
node '维护工具/重建汉化内核.js'
if ($LASTEXITCODE -ne 0) { throw '生成失败' }
node '维护工具/重建汉化内核.js' --check
if ($LASTEXITCODE -ne 0) { throw '生成后的资源仍不同步' }
```

这条命令会更新源码目录中的 `zh-bundle.js`，不会安装到客户端。改包装器时必须先审查包装器变更，不能指望仅注入两个常量的入口更新包装器。

### 7.2 分开维护三个版本

| 版本字段 | 何时更新 | 必须同步的位置 |
|---|---|---|
| 管理器产品版本 | 管理器正式发布 | csproj、发布文件名、元数据、README |
| 汉化内核版本 | 内核行为或资源发生发布变化 | 运行时版本、测试期望值、生成资源、安装验收记录 |
| 支持客户端版本 | 完成对应官方版本适配 | 适配清单、README、安装识别逻辑、验收记录 |

词条数从实际词库计算。检查数从实际测试结果计算。不要为了保持旧数字而跳过新增用例。下一次发版前增加版本一致性检查，拒绝源码、元数据、ZIP 文件名互相冲突。

### 7.3 编译到独立候选目录

下面的命令仅编译，不替换根目录 EXE 或已安装 ASAR。依赖首次安装需要 restore，不能在新环境直接照搬 `--no-restore`。

```powershell
$ErrorActionPreference = 'Stop'
Set-Location -LiteralPath 'D:\DSH\Antigravity ZH'

$SdkCommand = Get-Command dotnet -ErrorAction SilentlyContinue
$ReleaseDotNet = if ($SdkCommand) { $SdkCommand.Source } else {
    'C:\Users\24844\AppData\Local\dotnet\dotnet.exe'
}
if (-not (Test-Path -LiteralPath $ReleaseDotNet)) { throw '.NET SDK 未定位' }

node '维护工具/重建汉化内核.js' --check
if ($LASTEXITCODE -ne 0) { throw '资源不同步，停止编译' }
node '维护工具/状态标签回归.cjs'
if ($LASTEXITCODE -ne 0) { throw '回归失败，停止编译' }

$ReleaseStage = Join-Path (Get-Location).Path ('work\release-candidate\' + [Guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $ReleaseStage | Out-Null

& $ReleaseDotNet restore 'src/AntigravityZhManager/AntigravityZhManager.csproj' -r win-x64
if ($LASTEXITCODE -ne 0) { throw '还原依赖失败' }
& $ReleaseDotNet publish 'src/AntigravityZhManager/AntigravityZhManager.csproj' `
    -c Release -r win-x64 --self-contained true --no-restore -o $ReleaseStage
if ($LASTEXITCODE -ne 0) { throw '发布编译失败' }

$CandidateExe = Join-Path $ReleaseStage 'AntigravityZhManager.exe'
if (-not (Test-Path -LiteralPath $CandidateExe)) { throw '未找到候选 EXE' }
Get-FileHash -LiteralPath $CandidateExe -Algorithm SHA256
Write-Output "候选目录：$ReleaseStage"
```

后续必须对这个候选目录做资源与启动检查，再发布。不要为消除启动问题随意移除当前 `requireAdministrator` 清单；管理员权限的产品取舍需要独立评估和测试。

### 7.4 打包和正式替换

当前 `scripts/package-dist.js` 存在“先删除旧 ZIP，再生成”的失败窗口。正式发布前完成以下改造：

1. 读取统一版本配置，禁止硬编码 `1.0.0` 文件名。
2. 创建本次发布独有的暂存目录和临时 ZIP。
3. 只加入明确清单中的候选 EXE、README 等文件，禁止把历史产物和源码缓存意外打包。
4. 校验 ZIP 可完整解压、CRC 正确、文件集合正确、中文文件名正常、EXE 字节和哈希与候选文件相同。
5. 生成 SHA256 清单与发布元数据，在临时目录核对全部信息。
6. 所有检查完成后再替换正式产物。旧交付包在新包验证完成之前保留。
7. 清理仅本次创建的暂存目录；递归清理前验证绝对路径和归属。

这些步骤是待实现的发布入口要求。`work/status-label-release.py` 是本次验证的临时实现，存在版本及本机假设，迁移并参数化前不要把它当长期接口。

### 7.5 三方一致性怎样验

| 比较对象 | 比较方法 | 不能替代它的证据 |
|---|---|---|
| 字典 / 运行时源码 ↔ `zh-bundle.js` | 比较包中实际字典与脚本文本；语法有效 | 只比较词条数量 |
| 源码资源 ↔ 编译和发布资源 | 检查 EmbeddedResource 与发布程序实际资源 | 只看到 publish 成功 |
| 本次发布 bundle ↔ 安装 `app.asar` 的 bundle | 读取归档条目内容并比较 SHA256/字节 | 只看到安装成功或 v32 字样 |
| 候选 EXE ↔ 根目录 EXE ↔ ZIP 中 EXE | SHA256 相等 | 只比较文件名或大小 |
| 安装 ASAR ↔ 对应官方基线 | 完整结构校验和计划变更白名单 | 只看到客户端可启动 |

安装为独立步骤：先保存工作、确认客户端关闭、核对备份，再由管理器执行。安装之后重新做第 3 节验收，不能把编译回归直接当成安装后的结果。

**本阶段完成条件：**只有一个生成实现；发布包先验证后替换；源码、内嵌资源、候选程序、ZIP 与安装内容能够逐层追溯；版本和清单匹配。

## 8. 问题处理与日常工作方法

### 8.1 发现漏译时

提交一份最小问题记录：客户端版本、内核版本、触发步骤、原文、截图、所在控件、是否持续复现、是否包含变量。维护者按第 4 节分类后处理。正文中的英文通常属于内容，不按 UI 漏译计算。

### 8.2 发现误翻时

优先级高于新增词条。先缩小命中范围并增加保护用例，再修文案。若修改涉及整个聊天树、输入区或内容区，停止发布，直到正反向回归和现场证据都齐全。

### 8.3 常见问题

| 表现 | 排查顺序 |
|---|---|
| `--check` 提示资源不同步 | 确认当前词库和脚本是预期改动 → 运行规范生成入口 → 检查 Diff → 再检查 |
| 回归无法启动 Chrome | 检查当前固定路径 → 配置参数化路径 → 保持测试失败状态，不伪造通过 |
| SDK 找不到或 publish 失败 | 检查 .NET 8 SDK 路径和版本 → restore → 查看首次真实报错；保留当前产物 |
| 运行时版本正确但仍有英文 | 检查实际 DOM、保护根和属性 → 判断模板/拆分节点 → 增加结构用例 |
| 字典正确但已安装内容旧 | 逐层检查 bundle、编译资源、实际 EXE、安装归档；定位第一个不一致环节 |
| 官方更新后安装失败 | 记录新版本和基线哈希，进入适配流程；不强制套用旧锚点 |
| 恢复失败 | 检查客户端关闭、备份版本及哈希、文件权限；不删除唯一备份试错 |
| 日志说成功但现场没有对应控件 | 标记“未测试”，打开目标场景补证据 |

### 8.4 本地提交和发布授权

检查 Diff 并选择明确文件提交。测试源码、配置和脱敏夹具应进入版本管理；官方归档、会话转储、临时包和本机备份保持本地。不要用强制加入整个 `work` 的方式收集测试。

本指导书不授权 `git push`。本地检查、候选包生成、外部上传/推送和用户客户端安装应有清晰边界。用户已经授权的具体操作无需重复确认；未来新发布不能自动继承上次关闭客户端或推送的授权。

## 9. 开发任务与完成判定

按顺序完成，先解决“能否证明正确”，再扩大覆盖范围。

| 顺序 | 任务 | 产出 | 完成判定 |
|---|---|---|---|
| 1 | 原会话与新动作现场验收 | 截图、验收表 | 状态中文正确；目标/正文不变；未测项明列 |
| 2 | 当前检查入口与测试入库 | `scripts/check-current.ps1`、受管测试 | 干净克隆可运行；失败返回非零；无需历史目录 |
| 3 | 生成入口统一与版本一致性 | 单一生成实现和检查 | 双次生成一致；检查不写文件；三种版本可区分 |
| 4 | 词库与规则质量门禁 | 占位符、术语、例外、性能测试 | 未解释异常阻断；长输入超时可终止 |
| 5 | ASAR 备份清单和版本识别 | 版本/哈希清单 | 错版备份和未知客户端不会覆盖 |
| 6 | 注入命中数及临时归档校验 | 引擎加固、隔离测试 | 零/多锚点拒绝；校验失败原件不变 |
| 7 | 可恢复提交、恢复及归属清理 | 引擎与故障测试 | 失败可恢复；不按通用文件名误删 |
| 8 | 发布入口重构 | 候选包、验证清单 | 新包通过前旧包仍在；中文名/哈希/资源正确 |
| 9 | 深层界面覆盖 | 界面清单与正反向用例 | 权限、压缩、分支、空状态等逐项有结论 |
| 10 | Windows CI | 与本地同一入口 | 当前源码必需检查通过后才产出候选包 |

发布判定使用三个状态：**可发布 / 不可发布 / 待验收**。必需测试失败为不可发布；必需现场项缺失为待验收；只有全部必需条件满足才能判为可发布。不要只用一个汇总分数掩盖内容误翻、归档损坏或恢复失败。

日常执行时配合 `docs/维护执行清单.md`。详细历史审查与本次修复 Diff 保持在对应报告中，避免复制出多份互相冲突的事实记录。
